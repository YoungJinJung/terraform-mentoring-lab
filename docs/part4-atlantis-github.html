01

Atlantis의 개념과 동작

30분LEVEL 200

모듈 1~3에서 우리는 계속 로컬에서 apply했습니다. 그게 왜 팀에서 성립하지 않는지부터 봅니다.

로컬 apply가 만드는 세 가지 문제

  • 권한이 사람에게 있습니다. 인프라를 바꾸려면 개발자 개인이 프로덕션 권한을 가져야 합니다. 그 노트북이 곧 공격 표면입니다
  • 리뷰가 없습니다. 코드 리뷰는 하는데, 정작 plan 결과는 아무도 보지 않습니다. -/+가 떠도 본인만 압니다
  • 동시 실행이 깨집니다. 상태 잠금이 있어도, 두 사람이 서로 다른 브랜치를 번갈아 apply하면 인프라가 왔다 갔다 합니다

Atlantis가 하는 일

Atlantis는 GitHub 웹훅을 받아 PR 안에서 Terraform을 실행하고 결과를 코멘트로 남기는 오픈소스 서버입니다.

얻는 것 세 가지

협업

plan 결과가 PR에 그대로 붙습니다. 리뷰어가 무엇이 바뀌는지 코드가 아니라 결과로 봅니다. -/+가 뜨면 승인 전에 잡힙니다.

권한 분리

AWS 권한이 Atlantis의 Role에만 있습니다. 개발자 계정은 읽기 전용이어도 됩니다. 모듈 3의 SOPS 복호화 권한도 여기에만 줍니다.

감사

누가 언제 무엇을 승인해 무엇이 바뀌었는지가 PR 하나에 다 남습니다. CloudTrail과 함께 두 축이 됩니다.

잠금

Atlantis가 프로젝트 단위 잠금을 겁니다. 다른 PR이 같은 디렉터리를 plan하면 대기합니다. state 잠금보다 앞단에서 막습니다.

명령어

PR 코멘트동작
atlantis planplan 실행 (보통 push 시 자동 실행됨)
atlantis plan -d envs/dev특정 디렉터리만
atlantis plan -- -target=...-- 뒤는 terraform에 그대로 전달
atlantis applyapply 실행. 승인 요건을 만족해야 함
atlantis unlock이 PR이 잡고 있는 잠금 해제
atlantis approve_policies정책 검사 위반을 승인 (정책 검사 활성화 시)

보안버전을 고정하고 빠르게 올리세요

Atlantis는 PR 코멘트를 입력으로 받아 셸에서 Terraform을 실행하는 구조라, 입력 처리에서 취약점이 나오면 임팩트가 큽니다. 2026년에도 경로 순회·명령 주입 계열 취약점이 보고됐고, v0.47.1은 그 보안 패치 릴리스입니다.

:latest 태그를 쓰지 말고 버전을 고정하되, 릴리스 노트를 구독해 보안 패치는 빠르게 올리세요. 이미지는 이제 ghcr.io/runatlantis/atlantis에서 받습니다(Docker Hub는 deprecated).

02

사전 준비

30분LEVEL 200

Atlantis를 세우기 전에 네 가지가 필요합니다. 이걸 안 맞춰 놓고 시작하면 중간에 계속 막힙니다.

  1. AWS 권한 Atlantis가 맡을 IAM Role. 모듈 3의 LAB 01에서 만든 것을 씁니다. ECS Task Role로 붙일 것이므로 신뢰 주체는 ecs-tasks.amazonaws.com.
  2. GitHub 자격 증명 GitHub App(권장) 또는 봇 계정의 Personal Access Token. 아래에서 비교합니다.
  3. 실습 리포지토리 Terraform 코드가 들어갈 리포. 모듈 1~3에서 만든 modules/와 envs/ 구조를 올립니다.
  4. 도메인과 인증서 GitHub 웹훅은 HTTPS로 보냅니다. Route 53 도메인 + ACM 인증서 + ALB. 없으면 웹훅이 도달하지 못합니다.

GitHub App vs PAT

GitHub App봇 계정 PAT
웹훅App이 자체 처리 — 리포마다 웹훅을 만들 필요 없음리포마다 웹훅 수동 생성
권한App 단위로 세밀하게 부여봇 계정에 write 권한 + collaborator 필요
플래그--gh-app-id, --gh-app-key-file--gh-user, --gh-token
제약App당 설치(installation) 1개만 지원봇 계정 하나를 사람들이 공유하게 됨

공식 문서는 어느 쪽도 "권장"으로 못박지 않지만, 리포가 여러 개면 App이 확실히 편합니다 — 웹훅을 리포마다 만들지 않아도 되니까요. 실습은 리포 하나이므로 PAT로 시작해도 됩니다.

웹훅 시크릿을 반드시 설정하세요

--gh-webhook-secret이 없으면 인터넷의 누구나 Atlantis에 가짜 웹훅을 보낼 수 있습니다. ALB가 공개되어 있다는 점을 기억하세요. 이 값도 SOPS로 암호화해 커밋합니다.

03

Atlantis 구성

40분LEVEL 300

배포 형태 고르기

형태특징
ECS Fargate + ALB + EFS가장 흔한 AWS 패턴. 서버 관리 없음. plan 파일 영속을 위해 EFS. 이 실습에서 씁니다
EKS StatefulSet + PVC이미 EKS를 쓴다면. IRSA/Pod Identity로 권한 부여
EC2 단독가장 단순하지만 인스턴스 관리 부담

Atlantis는 상태를 디스크에 둡니다

plan 결과 파일을 디스크에 저장했다가 apply 때 그 파일을 씁니다. 그래서 인스턴스가 하나여야 하고(공식 매니페스트도 replicas: 1), 컨테이너가 재시작돼도 파일이 남아야 합니다.

ECS면 EFS 볼륨, 쿠버네티스면 StatefulSet + PVC. 이걸 빼먹으면 "plan은 됐는데 apply할 때 plan 파일이 없다"는 에러를 만납니다.

서버 설정

allowed_overrides가 보안의 핵심입니다. 이걸 열어두면 누구나 PR로 atlantis.yaml을 고쳐 승인 요건을 없앨 수 있습니다.

atlantis.yaml — 리포 설정

승인 요건 세 가지의 의미 300

  • approved — PR에 리뷰 승인이 있어야 apply 가능
  • mergeable — 브랜치 보호 규칙(상태 체크 등)을 통과해야 함
  • undiverged — main과 갈라져 있지 않아야 함. 이게 중요합니다 — 오래된 브랜치의 plan은 현재 상태를 반영하지 않습니다

세 개를 다 켜는 것이 기본값이어야 합니다.

커스텀 워크플로 — SOPS 연동

SOPS 복호화는 별도 단계가 필요 없습니다 — Atlantis의 Task Role에 KMS Decrypt 권한이 있으면 data "sops_file"이 알아서 복호화합니다. 모듈 3에서 Key Policy를 그렇게 나눠둔 이유입니다.

정책 검사 LEVEL 300

--enable-policy-checks를 켜면 plan 이후 conftest로 OPA 정책을 평가합니다. 위반이 있으면 apply가 막히고, atlantis approve_policies로 별도 승인을 받아야 합니다.

팀 allowlist를 쓸 때 주의

--gh-team-allowlist를 설정했다면 policy_check 명령을 반드시 allowlist에 추가해야 합니다. 정책 검사는 자동 실행되는데, allowlist에 없으면 실행 자체가 거부됩니다.

정책 승인(approve_policies)은 PR 머지 승인과 별개입니다. prevent_self_approve로 본인 승인을 막을 수 있습니다.

Atlantis 세우고 전환하기

50분 · 실습
LAB 01

ECS Fargate에 Atlantis 배포

  1. 모듈 2의 VPC 위에 ALB를 세웁니다. ACM 인증서를 붙이고 HTTPS 리스너를 만듭니다.
  2. ECS 클러스터와 Fargate 태스크 정의를 만듭니다. 이미지는 ghcr.io/runatlantis/atlantis:v0.47.1처럼 버전을 고정합니다.
  3. EFS 파일시스템을 만들어 /atlantis-data에 마운트합니다. 이걸 빼면 apply가 실패합니다.
  4. Task Role에 모듈 3에서 만든 인프라 권한과 KMS Decrypt를 붙입니다. Task Execution Role은 별도로 ECR·로그 권한만.
  5. GitHub PAT와 웹훅 시크릿을 SOPS로 암호화해 커밋하고, Terraform이 복호화해 Secrets Manager에 넣은 뒤 태스크 정의에서 secrets로 주입합니다.
  6. Route 53에 A 레코드(ALB alias)를 만들고, GitHub 리포에 웹훅을 등록합니다.
  7. https://atlantis.example.com/healthz로 살아있는지 확인합니다.
LAB 02

모듈 2·3의 코드를 PR로 재현하기

이 실습이 이 모듈의 핵심입니다. 같은 코드가 로컬에서 돌 때와 PR에서 돌 때 무엇이 달라지는지를 몸으로 확인합니다.

  1. atlantis.yaml을 리포 루트에 추가하고 커밋합니다.
  2. 모듈 2의 VPC 코드에서 nat_strategy를 single → per_az로 바꾸는 PR을 올립니다.
  3. PR에 자동으로 plan 결과가 붙는지 확인합니다. 안 붙으면 웹훅 전달 로그를 GitHub Settings에서 봅니다.
  4. 승인 없이 atlantis apply를 코멘트해 봅니다. 거부되어야 합니다. 어떤 메시지가 나오나요?
  5. 리뷰 승인을 받고 다시 atlantis apply. 성공하면 PR이 자동 머지되는지 봅니다(automerge: true).
  6. 두 번째 PR을 같은 디렉터리로 올리고 plan을 시도합니다. 잠금 메시지가 나오는지 확인하세요.
  7. 정책 검사 — SSH를 0.0.0.0/0으로 여는 PR을 올려 위 rego 정책에 걸리는지 봅니다.
  8. 확인 질문 — 로컬에서 여전히 terraform apply를 칠 수 있나요? 못 치게 하려면 무엇을 해야 하나요?

마지막 질문의 답

Atlantis를 세운 것만으로는 로컬 apply를 막지 못합니다. 사람의 IAM 권한을 읽기 전용으로 회수해야 실제로 닫힙니다. 그리고 GitHub 브랜치 보호로 main 직접 푸시를 막아야 합니다 — 다음 장의 주제입니다.

05

GitHub도 코드로

40분LEVEL 200~300

리포지토리 설정, 브랜치 보호, Actions 시크릿까지 Terraform으로 관리합니다. 콘솔에서 손으로 켠 설정이 하나도 남지 않게 하는 것이 목표입니다.

GitHub Provider

prevent_destroy를 꼭 거세요

실수로 terraform destroy하면 리포지토리가 통째로 삭제됩니다. 인프라와 달리 되돌리기가 훨씬 어렵습니다. 조직의 모든 리포를 Terraform으로 관리한다면 더더욱.

브랜치 보호 — ruleset이 신형입니다 LEVEL 300

세 가지 리소스가 있어 헷갈립니다.

리소스기반지금 상황
github_branch_protection_v3REST API유지 중. repository + branch로 지정
github_branch_protectionGraphQL API유지 중. repository_id(node_id 가능) + pattern
github_repository_rulesetRulesets API신형 권장 경로. 조직 레벨 ruleset도 가능

ruleset의 함정 300

target마다 쓸 수 있는 규칙이 다릅니다. branch/tag는 pull_request·required_status_checks 등을 쓰고, push는 file_path_restriction·max_file_size 같은 것만 지원합니다. 섞으면 validation 에러가 납니다.

push target에서는 conditions.ref_name을 설정하면 안 됩니다.

branch_name_pattern·commit_message_pattern 같은 패턴 규칙은 Enterprise 소유 리포에서만 동작합니다.

Actions 시크릿을 SOPS로

모듈 3에서 만든 SOPS 파이프라인이 여기서 완성됩니다. 사람이 GitHub 콘솔에서 시크릿을 입력하지 않습니다.

여기서도 state에 남습니다

plaintext_value는 sensitive로 표시되지만 state에는 그대로 저장됩니다. 모듈 3의 이야기와 같습니다.

더 나은 방법: data "github_actions_public_key"로 공개 키를 받아 encrypted_value를 넘기는 것. 다만 실습 범위에서는 plaintext_value로 진행하고 state 보호에 의존합니다.

이상적인 형태는 시크릿 자체를 아예 안 넣는 것입니다 — 모듈 3의 GitHub OIDC를 쓰면 AWS 자격 증명은 시크릿이 필요 없습니다. Role ARN만 넣으면 되고, 그건 비밀이 아닙니다.

이 모듈이 끝나면

  • 인프라 변경은 PR로만 들어갑니다
  • AWS 권한은 Atlantis Role에만 있습니다
  • 시크릿은 암호화된 채로 Git에 있고, 복호화는 Atlantis만 합니다
  • GitHub 리포 설정과 브랜치 보호도 코드입니다
  • GitHub Actions는 OIDC로 AWS에 붙습니다 — 액세스 키가 없습니다

모듈 5부터는 이 위에서 애플리케이션을 배포합니다.

팀에서 Terraform을 쓸 때 로컬 apply의 문제는?200

세 가지입니다. 권한 — 개발자 개인이 프로덕션 권한을 갖게 됩니다. 리뷰 부재 — plan 결과를 본인만 봅니다. 동시성 — state 잠금이 있어도 서로 다른 브랜치를 번갈아 apply하면 인프라가 왔다 갔다 합니다.

해결은 도구가 아니라 권한 회수가 먼저입니다. Atlantis를 세워도 사람에게 권한이 남아 있으면 로컬 apply는 계속 가능합니다.

Atlantis는 정확히 무엇을 하는가?200

GitHub/GitLab 웹훅을 받아 PR 컨텍스트에서 terraform plan·apply를 실행하고 결과를 PR 코멘트로 남기는 오픈소스 서버입니다.

PR에 push하면 자동으로 plan이 돌고, 리뷰 승인 후 atlantis apply 코멘트로 적용합니다. 프로젝트 단위 잠금으로 동시 실행도 막습니다.

TACOS(Terraform Automation and Collaboration Software) 범주의 셀프호스팅 오픈소스 선택지입니다.

Atlantis를 배포할 때 왜 영구 스토리지가 필요한가?300

Atlantis는 plan 결과를 디스크의 plan 파일로 저장했다가 apply 때 그 파일을 사용합니다. 컨테이너가 재시작되면 파일이 사라져 "plan 파일이 없다"는 에러가 납니다.

ECS면 EFS 볼륨, 쿠버네티스면 StatefulSet + PVC를 씁니다. 같은 이유로 인스턴스는 1개여야 합니다 — 공식 매니페스트도 replicas: 1입니다.

apply_requirements의 undiverged는 왜 필요한가?300

브랜치가 main과 갈라져 있으면 그 plan은 현재 인프라 상태를 반영하지 않습니다. 다른 PR이 먼저 머지됐다면 이 plan은 이미 낡은 것입니다.

undiverged를 켜면 main과 동기화된 브랜치에서만 apply할 수 있습니다. approved(리뷰 승인)·mergeable(브랜치 보호 통과)과 함께 세 개를 다 켜는 것이 기본값이어야 합니다.

Atlantis의 allowed_overrides는 왜 중요한가?300

리포의 atlantis.yaml은 PR로 수정할 수 있습니다. 서버 설정에서 override를 열어두면, 공격자나 실수한 개발자가 PR 하나로 apply_requirements를 없애고 승인 없이 apply할 수 있습니다.

그래서 서버 사이드 repos.yaml에서 무엇을 덮어쓸 수 있는지 명시적으로 제한하고, allow_custom_workflows는 기본적으로 끕니다.

Atlantis에서 GitHub App과 PAT 중 무엇을 쓰는가?200~300

리포가 여러 개면 GitHub App이 유리합니다 — App이 웹훅을 자체 처리하므로 리포마다 웹훅을 만들 필요가 없고, 권한도 App 단위로 세밀하게 줍니다.

PAT는 봇 계정에 write 권한과 collaborator 지정이 필요하고, 그 계정을 사람들이 공유하게 됩니다.

제약도 알아두면 좋습니다: Atlantis는 GitHub App당 설치(installation) 1개만 지원합니다.

Atlantis에 시크릿을 어떻게 주는가?300

AWS 권한은 시크릿을 주지 않습니다 — ECS Task Role이나 EKS Pod Identity로 부여합니다. 액세스 키를 환경변수로 넣는 건 안티패턴입니다.

GitHub 토큰과 웹훅 시크릿처럼 실제 비밀이 필요한 값은 SOPS로 암호화해 커밋하고, Terraform이 복호화해 Secrets Manager에 넣은 뒤 태스크 정의의 secrets로 주입합니다.

Terraform 코드 안의 시크릿(예: DB 비밀번호)은 Atlantis Task Role에 KMS Decrypt 권한만 주면 data "sops_file"이 apply 시점에 알아서 복호화합니다.

인프라 코드에 정책 검사를 어떻게 거는가?300

Atlantis의 --enable-policy-checks로 conftest(OPA/rego)를 plan 결과에 적용합니다. plan JSON의 resource_changes를 검사해 "SSH 전체 개방 금지", "필수 태그 확인" 같은 규칙을 강제합니다.

위반이 있으면 apply가 막히고 atlantis approve_policies로 별도 승인이 필요합니다. 이 승인은 PR 머지 승인과 독립이고, prevent_self_approve로 본인 승인을 막을 수 있습니다.

대안으로 Checkov·tfsec·Terrascan을 CI에서 돌리는 방법도 있습니다. 차이는 plan 결과를 보느냐(conftest) 코드를 보느냐(정적 분석)입니다.

GitHub 브랜치 보호를 Terraform으로 관리할 때 어떤 리소스를 쓰는가?300

세 가지가 있습니다. github_branch_protection_v3(REST 기반), github_branch_protection(GraphQL 기반), 그리고 github_repository_ruleset.

신형 권장 경로는 ruleset입니다. 조직 레벨 ruleset도 가능하고, bypass actor를 세밀하게 지정할 수 있습니다(예: Atlantis App만 우회 허용).

함정: ruleset은 target(branch/tag/push)마다 쓸 수 있는 규칙이 다르고, push target에서는 conditions.ref_name을 설정하면 안 됩니다.

GitHub Actions 시크릿을 Terraform으로 관리하면 무슨 문제가 있나?300

plaintext_value는 state에 평문으로 저장됩니다. GitHub 쪽으로는 암호화되어 전송되지만 state는 별개입니다.

완화책: data "github_actions_public_key"로 받은 공개 키로 encrypted_value를 만들어 넘기기, state 버킷 암호화·접근 제어 강화.

근본 해법은 시크릿을 아예 두지 않는 것입니다. AWS 인증은 OIDC로 하면 Role ARN만 있으면 되고, Role ARN은 비밀이 아닙니다.

Atlantis 대신 쓸 수 있는 도구는?200

관리형으로는 HCP Terraform(구 Terraform Cloud), Spacelift, env0, Scalr가 있고, GitHub Actions 기반 경량 대안으로 Digger, Terrateam이 있습니다.

선택 기준: Atlantis는 셀프호스팅 오픈소스라 비용이 인프라 값뿐이지만 운영을 직접 해야 합니다(보안 패치 포함). 관리형은 드리프트 감지·정책 엔진·비용 추정 같은 기능이 붙어 있지만 사용료가 있고 코드가 외부를 거칩니다.

Atlantis를 운영할 때 보안상 신경 쓸 점은?300

Atlantis는 PR 코멘트를 입력으로 받아 셸에서 Terraform을 실행하는 구조입니다. 입력 처리 취약점의 임팩트가 곧 인프라 전체 권한입니다.

실무 체크리스트: ① --repo-allowlist를 좁게 ② --gh-webhook-secret 필수(ALB가 공개되어 있음) ③ allowed_overrides 제한 ④ 이미지 버전 고정 + 보안 패치 신속 적용 ⑤ Task Role에 최소 권한 ⑥ ALB에 WAF나 소스 IP 제한.

2026년에도 경로 순회·명령 주입 계열 CVE가 보고됐으므로 릴리스 노트 구독이 실제로 중요합니다.
