01

IAM 이해하기

45분LEVEL 200

IAM은 "누가(인증) 무엇을 할 수 있는가(인가)"를 다룹니다. 이 장에서는 정책이 어떻게 평가되는지를 정확히 잡습니다.

네 가지 구성 요소

요소설명
User사람 또는 애플리케이션의 장기 자격 증명. 실무에서는 거의 만들지 않습니다
GroupUser의 묶음. 정책을 그룹에 붙여 관리
Role누구나 위임받을 수 있는 권한 집합. STS로 임시 자격 증명을 발급받습니다
Policy권한 문서. Identity-based(주체에 부착) / Resource-based(리소스에 부착)

Role이 핵심입니다. EC2 Instance Profile, ECS Task Role, EKS Pod Identity, GitHub Actions OIDC — 뒤에 나오는 모든 것이 Role입니다.

정책 평가 순서

  1. 기본은 암묵적 거부(implicit deny) 아무 정책도 없으면 아무것도 못 합니다.
  2. 명시적 거부(explicit Deny)가 최우선 어느 정책 하나에라도 Deny가 있으면 무조건 거부. 뒤집을 수 없습니다.
  3. 명시적 허용(Allow) Deny가 없고 Allow가 하나라도 있으면 허용.

여기에 조직 차원의 상한(SCP·RCP)과 권한 경계(Permissions Boundary), 세션 정책이 교집합으로 걸립니다. 하나라도 허용하지 않으면 통과하지 못합니다.

Identity-based vs Resource-based

Identity-based

User·Group·Role에 붙습니다. "이 주체가 무엇을 할 수 있는가."

Principal을 쓰지 않습니다 — 붙은 대상이 곧 주체입니다.

Resource-based

S3 버킷, KMS 키, SQS 큐 등 리소스에 붙습니다. "누가 이 리소스에 접근할 수 있는가."

Principal이 필수입니다. 크로스 계정 접근의 핵심입니다.

동일 계정과 크로스 계정의 결정적 차이 300

같은 계정: Identity-based 또는 Resource-based 중 하나만 허용해도 통과합니다(OR).

다른 계정: 양쪽 다 허용해야 통과합니다(AND). 호출자 계정의 Identity 정책이 허용하고, 리소스 계정의 Resource 정책도 허용해야 합니다.

"버킷 정책은 열었는데 왜 안 되지"의 90%가 이겁니다. KMS 키는 여기에 Key Policy까지 한 겹 더 있습니다.

STS와 AssumeRole

신뢰 정책과 권한 정책은 완전히 다른 것입니다. 신뢰 정책은 "누가 이 Role을 맡을 수 있나", 권한 정책은 "이 Role이 무엇을 할 수 있나". 이 구분이 안 되면 크로스 계정에서 반드시 막힙니다.

Principal: root는 루트 계정이 아닙니다

arn:aws:iam::111122223333:root는 "111122223333 계정 전체"를 뜻합니다. 즉 그 계정의 IAM 관리자가 누구에게든 이 Role을 맡길 권한을 줄 수 있다는 의미입니다. 신뢰 범위를 좁히려면 특정 Role ARN을 명시하세요.

CloudTrail — 누가 무엇을 했는가

AWS의 모든 동작은 API 호출입니다. CloudTrail이 호출자·시각·파라미터·소스 IP를 기록합니다. 콘솔의 이벤트 기록은 90일이며, 그 이상은 S3로 trail을 만들어 보관합니다.

모듈 4에서 Atlantis가 남기는 감사 로그와 함께, "인프라 변경 이력"의 두 축이 됩니다.

모듈 4·5에서 실제로 씁니다. 액세스 키를 GitHub Secrets에 넣는 방식은 이제 안티패턴입니다.

워크플로 쪽에는 permissions: id-token: write가 반드시 있어야 토큰이 발급됩니다. 액션은 aws-actions/configure-aws-credentials v6 계열이 현행입니다.

03

가드레일과 Best Practice

30분LEVEL 200~300

여덟 가지 원칙

  • Root 계정을 쓰지 않습니다. 계정 생성 직후 MFA를 걸고 봉인합니다
  • MFA를 강제합니다. 2025년 6월부터 모든 계정 유형의 root MFA가 의무화됐습니다. FIDO2 패스키를 지원하고 root당 최대 8개까지 등록됩니다
  • 장기 액세스 키를 만들지 않습니다. Role + STS로 대체합니다. 이미 있다면 정기 교체와 미사용 키 삭제
  • 최소 권한. *로 시작하지 말고 필요한 액션만 추가합니다
  • 조건(Condition)을 답니다. 소스 IP, MFA 여부, 태그, 리전 등
  • 미사용 리소스를 정리합니다. Access Analyzer의 미사용 액세스 분석이 찾아줍니다
  • 멀티 계정 가드레일. SCP와 RCP로 상한을 겁니다
  • 활동을 모니터링합니다. CloudTrail + Access Analyzer + GuardDuty

2024 신규SCP와 RCP는 다른 것입니다 300

SCP(Service Control Policy)는 "우리 계정의 principal이 무엇을 할 수 있는가"의 상한입니다.

RCP(Resource Control Policy, 2024년 11월 신규)는 "우리 리소스에 누가 접근할 수 있는가"의 상한입니다. 외부 principal도 포함합니다.

둘 다 권한을 부여하지 않고 상한만 설정합니다. 유효 권한 = RCP ∩ SCP ∩ (Identity 정책 ∪ Resource 정책). RCP는 멤버 계정에만 적용되고 관리 계정 리소스와 서비스 연결 역할은 제외됩니다.

데이터 퍼리미터(우리 데이터가 조직 밖으로 나가지 못하게)를 만들 때 RCP가 결정적입니다. 출시 당시 S3·STS·KMS·SQS·Secrets Manager였고 현재 40여 개 서비스로 확대됐습니다.

초안으로 쓰고 반드시 손보세요. 그대로 붙이면 빠진 권한 때문에 운영에서 터집니다.

중앙 root 액세스 관리 LEVEL 300

2024년 11월부터 Organizations의 관리 계정이 멤버 계정의 root 자격 증명을 삭제할 수 있습니다. 두 기능이 별도로 존재합니다.

  • EnableOrganizationsRootCredentialsManagement — 멤버 계정 root의 비밀번호·액세스 키·MFA를 제거
  • EnableOrganizationsRootSessions — 필요할 때 sts:AssumeRoot로 특권 작업 수행

IAM Identity Center가 전제 조건이 아닙니다. Organizations만 있으면 됩니다.

05

KMS

30분LEVEL 200~300

S3·EBS·Secrets Manager·SOPS가 전부 KMS 위에서 돌아갑니다. 봉투 암호화만 이해하면 나머지는 응용입니다.

키의 세 가지 종류

종류제어권비용
고객 관리형 키(CMK)키 정책·로테이션·삭제 전부 제어. 실무에서 쓰는 것키당 월정액 + 사용량
AWS 관리형 키aws/s3 같은 별칭. 연 1회 자동 로테이션 강제, 비활성화 불가월정액 없음
AWS 소유 키가시성 없음. AWS 내부용무료

봉투 암호화 — 왜 이렇게 하나

KMS는 4KB를 넘는 데이터를 직접 암호화하지 않습니다. 대신 데이터 키를 발급하고, 실제 암호화는 클라이언트가 합니다.

  1. GenerateDataKey KMS가 데이터 키를 두 벌 줍니다 — 평문 키와, KMS 키로 암호화된 키.
  2. 암호화 평문 데이터 키로 데이터를 암호화하고, 평문 키는 메모리에서 즉시 폐기합니다.
  3. 보관 암호화된 데이터 + 암호화된 데이터 키를 함께 저장합니다.
  4. 복호화 KMS에 암호화된 데이터 키를 보내 평문 키를 받고, 그걸로 데이터를 복호화합니다.

이 구조 덕분에 대용량 데이터도 KMS 호출 한 번으로 처리되고, 키 자체는 KMS 밖으로 평문으로 나가지 않습니다. SOPS가 하는 일도 정확히 이것입니다.

2024 변경로테이션이 유연해졌습니다

자동 로테이션 주기를 90일 ~ 2560일(7년) 사이에서 지정할 수 있게 됐습니다(기본 365일). RotateKeyOnDemand로 즉시 로테이션도 가능합니다.

과금도 바뀌었습니다 — 로테이션 1·2회차까지만 추가 요금이 붙고 3회차부터는 무과금입니다. 예전에 "로테이션은 비싸다"고 배웠다면 지금은 다릅니다.

자동 로테이션은 대칭 암호화 키(AWS_KMS origin)만 지원합니다. 비대칭·HMAC·임포트 키는 온디맨드만 가능합니다.

Key Policy — 잊기 쉬운 한 겹

Key Policy에서 root를 빼면 키가 잠깁니다

KMS는 IAM 정책만으로 접근할 수 없습니다. Key Policy가 반드시 허용해야 합니다. root 문장을 빼고 잘못 만들면 아무도 그 키를 관리할 수 없게 되고 AWS 지원을 불러야 합니다.

실습에서도 이 문장은 항상 넣으세요.

선택 기준 한 줄

자동 로테이션·크로스 계정 공유·랜덤 비밀번호 생성이 필요하면 Secrets Manager. 단순 설정값이거나 비용을 아껴야 하면 Parameter Store(SecureString).

주의: Parameter Store에서 "높은 처리량" 옵션을 켜면 표준 파라미터에도 API 호출 요금이 붙습니다. 저장 비용이 호출 비용으로 옮겨갈 뿐입니다.

또 "API interaction"은 요청 1건이 아니라 파라미터 1개 단위입니다. 10개를 한 번에 조회해도 10건으로 계산됩니다.

로테이션의 현실

Secrets Manager 로테이션은 Lambda 함수가 4단계(createSecret → setSecret → testSecret → finishSecret)를 수행합니다. RDS 등 AWS 서비스는 관리형 로테이션 함수가 제공됩니다.

  • 스케줄은 rate() 또는 cron()(UTC), 최소 주기 4시간
  • Lambda에 Secrets Manager 서비스 주체의 lambda:InvokeFunction 권한이 필요합니다
  • Lambda가 DB에 도달할 네트워크 경로가 있어야 합니다 — VPC 안의 RDS면 Lambda도 VPC에 넣어야 합니다. 여기서 대부분 막힙니다

그런데 왜 SOPS가 또 필요한가

Secrets Manager에 값을 넣으려면 누군가 그 값을 콘솔이나 CLI로 입력해야 합니다. 그 순간 "사람이 손으로 한 설정"이 코드 밖에 생기고, 인프라를 재현할 수 없게 됩니다.

SOPS는 암호화된 값을 Git에 커밋해서 이 문제를 없앱니다. 다음 장의 주제입니다.

SOPS

30분 · 실습LEVEL 300

시크릿을 암호화된 채로 Git에 커밋하고, Terraform이 apply 시점에 복호화합니다. 이 모듈의 결론입니다.

SOPS가 하는 일

SOPS(Secrets OPerationS)는 YAML·JSON·ENV 파일의 값만 암호화하고 키는 평문으로 남깁니다. 그래서 diff가 읽힙니다 — 어떤 항목이 바뀌었는지는 보이고, 값은 안 보입니다.

2015년 Mozilla에서 시작해 현재 CNCF Sandbox 프로젝트이며 getsops 조직이 관리합니다. AWS KMS·GCP KMS·Azure Key Vault·age·PGP를 지원합니다.

.sops.yaml — 규칙 파일

이 파일이 있으면 sops encrypt가 경로만 보고 알아서 맞는 키를 씁니다. 환경별로 키를 분리하는 것이 핵심입니다 — dev 키를 가진 사람이 prod 시크릿을 열 수 없어야 합니다.

updatekeys와 rotate의 차이 300

updatekeys는 마스터 키 목록만 갱신합니다. 팀원이 나가거나 새 KMS 키를 추가할 때 씁니다. 데이터 키는 그대로입니다.

rotate는 데이터 키를 새로 생성합니다. 시크릿이 유출됐다고 의심될 때 씁니다.

SOPS 팀은 일상적인 키 접근 관리에는 updatekeys를 권장합니다.

Terraform에서 읽기

중요 — data "sops_file"은 state에 평문을 남깁니다

복호화된 값이 state 파일에 그대로 저장됩니다. 모듈 1에서 만든 state 버킷의 암호화와 접근 제어가 여기서 실제로 일하는 것입니다.

SOPS로 시크릿 파이프라인 만들기

  1. SOPS를 설치합니다 (brew install sops).
  2. 5장의 KMS 키를 만들고, Key Policy에서 내 개발자 Role은 Encrypt만, Atlantis Role은 Decrypt까지 허용합니다.

IAM · 암호화

클릭하면 답이 열립니다. 먼저 스스로 답해 보고 여세요.

IAM 정책은 어떤 순서로 평가되는가?200

기본은 암묵적 거부. 그 위에 명시적 Deny가 최우선이고, Deny가 없으면 Allow가 하나라도 있을 때 허용됩니다.

여기에 조직 상한(SCP·RCP), 권한 경계, 세션 정책이 교집합으로 걸립니다. "Allow가 있는데 왜 안 되지"는 대부분 이 중 하나가 막고 있는 겁니다.

Identity-based와 Resource-based 정책의 차이, 그리고 크로스 계정에서 달라지는 점은?200~300

Identity-based는 주체(User·Role)에 붙고 Principal이 없습니다. Resource-based는 리소스에 붙고 Principal이 필수입니다.

같은 계정에서는 둘 중 하나만 허용해도 통과(OR)하지만, 다른 계정에서는 양쪽 다 허용해야 합니다(AND). 크로스 계정 S3 접근이 안 되는 이유의 대부분입니다.

신뢰 정책과 권한 정책의 차이는?200

신뢰 정책은 "누가 이 Role을 맡을 수 있는가"(sts:AssumeRole의 Principal), 권한 정책은 "이 Role이 무엇을 할 수 있는가"입니다.

Role을 만들 때 두 개를 다 써야 하고, 하나만 맞으면 동작하지 않습니다. Terraform에서는 assume_role_policy가 신뢰 정책입니다.

액세스 키 대신 Role을 쓰라고 하는 이유는?200

액세스 키는 만료되지 않는 장기 자격 증명입니다. 코드·환경변수·CI 설정에 남고, 유출돼도 알기 어렵고, 교체가 번거롭습니다.

Role은 STS가 수 시간짜리 임시 자격 증명을 발급합니다. 유출돼도 곧 만료되고, CloudTrail에 어느 Role의 어떤 세션인지 남습니다.

실무 답: EC2는 Instance Profile, ECS는 Task Role, EKS는 Pod Identity, GitHub Actions는 OIDC. 액세스 키를 만들 자리가 사실상 없습니다.

ECS의 Task Execution Role과 Task Role의 차이는?200~300

Task Execution Role은 ECS 에이전트가 씁니다 — ECR 이미지 풀, CloudWatch 로그 스트림 생성, Secrets Manager/SSM에서 환경변수 주입.

Task Role은 컨테이너 안의 애플리케이션이 씁니다 — S3, DynamoDB, SQS 등.

구분법: 태스크가 아예 안 뜨면 Execution Role, 떴는데 앱이 AccessDenied면 Task Role.

IRSA와 EKS Pod Identity 중 무엇을 쓰는가?300

EKS라면 Pod Identity가 현재 AWS 권장입니다. OIDC Provider가 필요 없어 계정당 100개 한도를 피하고, 같은 Role을 여러 클러스터에서 재사용할 수 있으며, 세션 태그로 ABAC이 됩니다.

IRSA가 필요한 경우는 EKS가 아닌 쿠버네티스(EKS Anywhere, EC2 위 셀프 매니지드)입니다. Pod Identity는 EKS 전용입니다.

크로스 계정은 2025년 6월부터 Pod Identity도 role chaining으로 지원합니다.

GitHub Actions에서 AWS에 인증하는 안전한 방법은?300

OIDC federation입니다. GitHub이 발급한 JWT로 sts:AssumeRoleWithWebIdentity를 호출하므로 장기 액세스 키를 Secrets에 저장할 필요가 없습니다.

구성: aws_iam_openid_connect_provider(token.actions.githubusercontent.com) + Role의 신뢰 정책에 aud = sts.amazonaws.com과 sub 조건. 워크플로에는 permissions: id-token: write.

가장 흔한 실수는 sub를 repo:org/*처럼 넓게 여는 것입니다. 조직 내 아무 리포지토리나 그 Role을 쓸 수 있게 됩니다. 브랜치나 환경까지 고정하세요.

2026년 4월 GitHub이 immutable subject claims를 도입해, 2026-07-15 이후 만든 리포는 sub에 조직 ID·리포 ID가 붙습니다. 옛 예제를 그대로 쓰면 실패합니다.

SCP와 RCP의 차이는?300

SCP는 "우리 조직의 principal이 무엇을 할 수 있는가"의 상한, RCP(2024-11 신규)는 "우리 리소스에 누가 접근할 수 있는가"의 상한입니다. RCP는 조직 밖 principal에도 적용됩니다.

둘 다 권한을 부여하지 않고 상한만 설정합니다. 유효 권한은 RCP ∩ SCP ∩ (Identity ∪ Resource) 정책입니다.

데이터 퍼리미터를 만들 때 RCP가 필요합니다. SCP만으로는 "외부 계정이 우리 S3를 읽는 것"을 막을 수 없습니다.

KMS의 봉투 암호화를 설명하라200~300

KMS는 4KB 초과 데이터를 직접 암호화하지 않습니다. 대신 GenerateDataKey로 평문 데이터 키와 암호화된 데이터 키를 함께 발급합니다.

클라이언트가 평문 키로 데이터를 암호화하고 평문 키는 즉시 폐기, 암호화된 데이터와 암호화된 데이터 키를 함께 보관합니다. 복호화할 때 KMS에 암호화된 키를 보내 평문 키를 받아옵니다.

이점: 대용량도 KMS 호출 한 번, 키가 평문으로 KMS를 벗어나지 않음, KMS 처리량 한도에 걸리지 않음.

KMS Key Policy를 잘못 만들면 어떤 일이 생기는가?300

KMS는 IAM 정책만으로 접근할 수 없습니다. Key Policy가 반드시 허용해야 합니다.

그래서 Key Policy에서 계정 root를 허용하는 문장을 빼고 잘못 만들면 아무도 그 키를 관리할 수 없는 상태가 되고, AWS 지원에 문의해야 복구됩니다. 실무에서 실제로 일어나는 사고입니다.

Secrets Manager와 Parameter Store 중 무엇을 언제 쓰는가?200

Secrets Manager: 자동 로테이션이 필요하거나, 크로스 계정으로 공유하거나, DB 자격 증명처럼 JSON으로 묶어 관리할 때. 시크릿당 월 요금이 있습니다.

Parameter Store: 단순 설정값, 비용 최소화. 표준 파라미터는 무료이고 SecureString으로 KMS 암호화가 됩니다.

덧붙이면 좋은 것: Parameter Store에서 "높은 처리량"을 켜면 표준 파라미터에도 API 요금이 붙어 비용 이점이 사라집니다.

SOPS는 왜 쓰는가? Secrets Manager가 있는데도?300

Secrets Manager에 값을 넣으려면 누군가 손으로 입력해야 합니다. 그러면 코드 밖에 사람이 만든 설정이 생기고, 인프라를 코드만으로 재현할 수 없습니다.

SOPS는 값을 암호화된 채로 Git에 커밋합니다. 키 이름은 평문이라 diff가 읽히고, 값은 KMS 키를 가진 주체만 복호화합니다.

둘은 배타적이지 않습니다. 실무에서는 SOPS로 커밋한 값을 Terraform이 복호화해 Secrets Manager에 넣는 조합을 씁니다.

SOPS를 Terraform에서 쓸 때 주의할 점은?300

data "sops_file"로 읽은 값은 state에 평문으로 저장됩니다. 암호화된 파일을 Git에 안전하게 올려놓고 state 버킷을 방치하면 의미가 없습니다.

대응: state 버킷 암호화·접근 제어를 조이고, Terraform 1.10+ 라면 ephemeral "sops_file"과 write-only 속성을 써서 state에 남기지 않습니다.

또 KMS Key Policy로 개발자는 Encrypt만, 자동화 주체만 Decrypt로 나눠야 SOPS의 의미가 삽니다.

Access Analyzer의 정책 생성 기능을 그대로 믿어도 되는가?300

초안으로만 씁니다. CloudTrail 관리 이벤트 기반이라 S3 데이터 이벤트와 iam:PassRole을 포착하지 못합니다. 최대 90일 범위이므로 분기 배치 작업처럼 드문 액션도 빠집니다.

생성 결과는 콘솔에 7일 보관되고 계정당 동시 1건입니다. 그대로 적용하면 빠진 권한 때문에 운영에서 터집니다.

체크리스트 — 모듈 4로 넘어가기 전에

  • 명시적 Deny가 왜 최우선인지, 조직 상한이 어떻게 교집합으로 걸리는지 안다
  • 신뢰 정책과 권한 정책을 구분해서 쓸 수 있다
  • ECS의 두 Role 차이를 증상으로 구분할 수 있다

  • 봉투 암호화를 그림 없이 말로 설명할 수 있다
  • KMS Key Policy에 root 문장을 왜 남기는지 안다
  • SOPS로 암호화한 파일을 Terraform이 복호화해 리소스를 만들어 봤다
  • state에 시크릿이 남는다는 것을 직접 확인했다
