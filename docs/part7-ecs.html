Container와 VM

VM은 하이퍼바이저 위에 게스트 OS를 통째로 올립니다. 컨테이너는 호스트 커널을 공유하고 네임스페이스·cgroup으로 프로세스를 격리합니다.

격리가 약하다는 것의 의미 300

컨테이너는 커널을 공유하므로 커널 취약점은 컨테이너 경계를 넘습니다. 그래서 멀티 테넌트 환경에서는 Firecracker(Fargate가 쓰는 마이크로 VM)나 gVisor 같은 추가 격리를 씁니다.

Fargate는 태스크마다 별도 마이크로 VM에서 돌아 EC2 모드보다 격리가 강합니다. 이것이 Fargate를 고르는 이유 중 하나입니다.

서비스 디스커버리 — Service Connect vs Service Discovery LEVEL 300

Service Discovery (구형)

Cloud Map + Route 53 프라이빗 DNS. 태스크가 뜨면 DNS 레코드로 등록됩니다.

한계: DNS 캐싱 때문에 태스크가 죽어도 클라이언트가 계속 그 IP로 갑니다. 로드밸런싱도 DNS 라운드로빈뿐입니다.

Service Connect (권장)

각 태스크에 프록시 사이드카를 자동 주입합니다. 짧은 이름(orders:8080)으로 호출합니다.

라운드로빈 + outlier detection(문제 있는 대상 자동 제외), 재시도, 트래픽 지표를 ECS·CloudWatch에 제공합니다.

기능 자체는 추가 비용이 없습니다(태스크 리소스를 공유).

Service Connect를 쓰려면 Task Definition의 portMappings에 name이 반드시 있어야 합니다. 이걸 빼먹는 실수가 흔합니다.

ECS Exec — 컨테이너 안으로 들어가기 LEVEL 300

  • SSM Session Manager 기반이라 SSH도 베스천도 필요 없습니다
  • Task Role에 ssmmessages:CreateControlChannel 등 4개 액션이 필요합니다
  • 서비스나 태스크에 enableExecuteCommand가 켜져 있어야 하고, 이미 뜬 태스크에는 소급 적용되지 않습니다
  • 제약: 읽기 전용 루트 파일시스템 불가, 유휴 20분 타임아웃, 인터넷이 없으면 ssmmessages VPC Endpoint 필요
  • 클러스터 설정으로 세션 로그를 CloudWatch/S3에 남길 수 있고, CloudTrail에 ExecuteCommand가 기록됩니다

Fargate

  • 서버를 관리하지 않습니다. CPU·메모리만 지정하면 AWS가 마이크로 VM을 띄웁니다
  • CPU 0.25 vCPU부터 32 vCPU(2026-06 추가, 최대 244GB)까지. 8 vCPU 이상은 플랫폼 버전 1.4.0 이상
  • 메모리는 CPU에 따라 선택지가 정해져 있습니다 — 임의 조합이 안 됩니다
  • Fargate Spot: 최대 70% 저렴하지만 2분 전 통보 후 회수됩니다. 2024년부터 Graviton(ARM64)도 지원합니다

2025 신규ECS Managed Instances

Fargate와 EC2 사이의 선택지가 하나 늘었습니다. vCPU·메모리·아키텍처 요구만 지정하면 AWS가 사용자 계정 안의 EC2를 자동 프로비저닝·패치합니다.

Fargate와 달리 EC2의 전체 기능(GPU, 대용량 로컬 NVMe 등)을 쓸 수 있고, 기존 EC2 용량 공급자와 달리 인스턴스를 직접 관리하지 않습니다. 대신 EC2 비용 + 관리 요금 구조입니다.

03

용량 공급자

30분LEVEL 300

EC2 모드에서 "태스크를 더 띄우고 싶은데 인스턴스가 부족하다"를 자동으로 푸는 장치입니다. 계산식까지 이해해야 스케일이 왜 그렇게 도는지 설명할 수 있습니다.

전략과 가중치

base는 하나의 공급자에만 지정할 수 있습니다. "최소 이만큼은 안정적인 곳에" 라는 뜻이고, Spot 회수에 대비하는 기본 패턴입니다.

CapacityProviderReservation — 스케일 판단의 수식

EC2 용량 공급자의 managed scaling은 이 지표 하나로 인스턴스를 늘리고 줄입니다.

Target을 100 미만으로 두면 300

예를 들어 Target을 80으로 두면 "필요한 것보다 25% 더" 인스턴스를 유지합니다. 여유 용량을 미리 확보해 태스크 배치가 빨라지지만 비용이 올라갑니다.

급격한 트래픽 스파이크가 있는 서비스에서 쓰는 튜닝입니다.

Managed 기능 세 가지

  • Managed Scaling — 위 지표로 ASG의 desired를 ECS가 조정합니다. ASG의 desired는 0으로 시작하고 ECS가 관리합니다
  • Managed Termination Protection — 태스크가 도는 인스턴스를 스케일 인 대상에서 보호합니다. 이걸 끄면 태스크가 도는 인스턴스가 갑자기 종료됩니다
  • Managed Instance Draining — 인스턴스 종료 시 태스크를 안전하게 중지·재배치합니다. 최대 48시간까지 종료를 지연시킵니다. 기본값이 ON입니다

ASG 용량 공급자와 Fargate 용량 공급자는 같은 전략에 섞을 수 없습니다.

04

배포 전략

40분LEVEL 300

2025 변경 · 중요ECS가 Blue/Green을 자체 지원합니다

오래된 자료는 전부 "ECS Blue/Green = CodeDeploy"라고 씁니다. 2025년 7월부터 ECS 서비스 자체가 Blue/Green을 지원하고, 2025년 10월에는 Linear·Canary까지 추가됐습니다.

즉 deployment_controller.type을 CODE_DEPLOY로 바꾸지 않고, 기본값 ECS인 채로 deployment_configuration.strategy만 바꾸면 됩니다.

Terraform AWS Provider도 발표 당일(v6.4.0) 대응했습니다.

네 가지 전략

전략strategy동작
RollingROLLING기본값. minimumHealthyPercent·maximumPercent 범위에서 순차 교체
Blue/GreenBLUE_GREEN새 버전 전체를 띄우고 테스트 트래픽 → 운영 트래픽 전환 → bake → 옛 버전 종료
LinearLINEAR일정 비율씩 일정 간격으로 전환
CanaryCANARY소수 비율 먼저 → bake → 나머지 일괄 전환

Blue/Green 계열은 ALB, NLB, 또는 Service Connect가 있어야 합니다. LB가 없는 headless 서비스는 트래픽 전환 없이 태스크만 교체됩니다.

Lifecycle Hook — 검증 단계 끼워넣기 LEVEL 300

배포 각 단계에서 Lambda를 호출해 진행할지 롤백할지 결정할 수 있습니다.

Lambda는 hookStatus로 세 가지를 반환합니다 — SUCCEEDED(진행), FAILED(롤백), IN_PROGRESS(나중에 다시 호출). IN_PROGRESS를 반복 반환하면 Lambda의 15분 타임아웃을 넘어 최대 24시간까지 검증을 이어갈 수 있습니다.

Deployment Circuit Breaker LEVEL 300

Rolling 전용입니다

Circuit breaker는 ROLLING 배포에서만 동작합니다. 태스크가 RUNNING에 도달하지 못하거나 헬스체크에 실패한 횟수를 세다가 임계를 넘으면 배포를 실패 처리하고, rollback = true면 마지막 정상 배포로 되돌립니다.

Blue/Green 계열의 안전장치는 lifecycle hook + CloudWatch 알람 + bake time입니다. 둘을 섞어 설명하지 마세요.

2026년 7월부터 임계값을 조정할 수 있게 됐습니다(BOUNDED_PERCENT 기본 50%, UNBOUNDED_PERCENT, COUNT). 단, Terraform provider는 아직 이 설정을 지원하지 않습니다 — 기능 요청이 열려 있는 상태입니다.

ECS · 컨테이너
컨테이너와 VM의 차이는?200

VM은 하이퍼바이저 위에 게스트 OS를 통째로 올리고, 컨테이너는 호스트 커널을 공유하며 네임스페이스·cgroup으로 격리합니다.

그래서 컨테이너는 이미지가 MB 단위, 시작이 초 단위입니다. 대신 커널을 공유하므로 격리가 약합니다 — 커널 취약점은 컨테이너 경계를 넘습니다.

덧붙이면 좋은 것: Fargate는 태스크마다 별도 마이크로 VM(Firecracker)에서 돌아 EC2 모드보다 격리가 강합니다.

ECS의 Task Definition, Task, Service를 구분하라200

Task Definition은 설계도(이미지·CPU·메모리·포트·IAM·로그)이고 revision 버전이 있습니다. Task는 그 설계도로 실제 실행된 인스턴스입니다. Service는 Task를 지정 개수만큼 유지하고 LB 연결과 배포를 관리합니다.

쿠버네티스에 대응하면 Task ≈ Pod, Service ≈ Deployment + Service입니다.

awsvpc 네트워크 모드의 장단점은?300

장점: Task마다 ENI와 VPC IP를 받아 보안 그룹을 Task 단위로 적용할 수 있습니다. Flow Logs로 태스크별 트래픽도 보입니다. Fargate는 이 모드만 지원합니다.

단점: IP를 많이 씁니다. 태스크 수만큼 VPC IP가 필요해 서브넷이 작으면 고갈됩니다. EC2 모드에서는 인스턴스 타입별 ENI 한도 때문에 인스턴스당 태스크 수도 제한됩니다(ENI trunking으로 완화).

Task Execution Role과 Task Role의 차이는?200~300

Execution Role은 ECS 에이전트가 씁니다 — ECR 이미지 풀, CloudWatch 로그 생성, Secrets Manager/SSM에서 시크릿 주입.

Task Role은 컨테이너 안 애플리케이션이 씁니다 — S3, DynamoDB 등.

증상으로 구분: 태스크가 안 뜨면 Execution Role, 떴는데 앱이 AccessDenied면 Task Role.

CapacityProviderReservation을 설명하라300

EC2 용량 공급자의 managed scaling이 쓰는 지표입니다. M / N × 100이고, M은 (현재 실행 중 + 추가 필요) 태스크를 모두 돌리는 데 필요한 인스턴스 수, N은 현재 Running 인스턴스 수입니다.

Target은 보통 100. 150이면 부족하니 스케일 아웃, 50이면 남으니 스케일 인.

특수 케이스도 말하면 좋습니다: M=0·N=0이면 100(균형), M>0·N=0이면 200(인스턴스가 없는데 태스크가 필요 → 즉시 스케일 아웃).

Target을 100 미만(예: 80)으로 두면 여유 용량을 미리 확보해 배치가 빨라지지만 비용이 올라갑니다.

용량 공급자의 base와 weight는?300

base는 "먼저 이만큼은 무조건 이 공급자로"이고 하나의 공급자에만 지정할 수 있습니다. weight는 base를 채운 뒤 나머지를 나누는 비율입니다.

전형적 패턴: FARGATE base=2 weight=1, FARGATE_SPOT base=0 weight=4. Spot이 전부 회수돼도 최소 2개는 살아있습니다.

제약: ASG 용량 공급자와 Fargate 용량 공급자를 같은 전략에 섞을 수 없습니다.

ECS에서 Blue/Green 배포를 어떻게 하는가?300 · 최신

예전에는 deployment_controller.type = "CODE_DEPLOY"로 CodeDeploy에 맡겼습니다. 2025년 7월부터 ECS 서비스 자체가 지원하고, 2025년 10월에 Linear·Canary도 추가됐습니다.

지금은 deployment_controller.type = "ECS"인 채로 deployment_configuration.strategy = "BLUE_GREEN"과 bake_time_in_minutes를 설정하고, load_balancer.advanced_configuration에 green 타겟 그룹과 production/test 리스너 규칙을 지정합니다.

네이티브가 유리한 점: Service Connect·headless 서비스 지원, lifecycle hook이 IN_PROGRESS 반환으로 최대 24시간까지 검증 가능(CodeDeploy는 총 1시간).

이 답을 하면 최신 정보를 따라간다는 신호가 확실히 됩니다 — 대부분의 자료가 아직 CodeDeploy 기준입니다.

Deployment circuit breaker는 어떤 배포에서 동작하는가?300

Rolling 배포에서만 동작합니다. 태스크가 RUNNING에 도달하지 못하거나 헬스체크에 실패한 횟수를 세다가 임계를 넘으면 배포를 실패 처리하고, rollback = true면 마지막 정상 배포로 되돌립니다.

Blue/Green 계열의 안전장치는 lifecycle hook + CloudWatch 알람 + bake time으로 다릅니다. 이 둘을 섞어 말하면 감점입니다.

2026년 7월부터 임계값 설정이 가능해졌지만 Terraform provider는 아직 미지원입니다.

Service Connect와 Service Discovery의 차이는?300

Service Discovery는 Cloud Map + Route 53 프라이빗 DNS입니다. DNS 캐싱 때문에 죽은 태스크로 계속 요청이 가는 문제가 있고, 로드밸런싱도 DNS 라운드로빈뿐입니다.

Service Connect는 각 태스크에 프록시 사이드카를 자동 주입합니다. 짧은 이름으로 호출하고, 라운드로빈 + outlier detection + 재시도가 되며, 트래픽 지표가 ECS·CloudWatch에 나옵니다.

주의: Task Definition의 portMappings에 name이 반드시 있어야 합니다.

ECS 컨테이너 안에 어떻게 들어가는가?300

ECS Exec입니다. SSM Session Manager 기반이라 SSH나 베스천이 필요 없습니다.

필요 조건: Task Role에 ssmmessages:CreateControlChannel/CreateDataChannel/OpenControlChannel/OpenDataChannel, 서비스에 enableExecuteCommand. 이미 뜬 태스크에는 소급 적용되지 않아 새 태스크부터 됩니다.

제약도 말하면 좋습니다: 읽기 전용 루트 파일시스템 불가, 유휴 20분 타임아웃, 인터넷 없으면 ssmmessages VPC Endpoint 필요. 세션 로그는 CloudWatch/S3에 남기고 CloudTrail에 감사 기록됩니다.

ECS에 시크릿을 어떻게 주입하는가?200~300

Task Definition의 secrets 필드에 Secrets Manager나 Parameter Store의 ARN 참조를 넘깁니다. 실제 값은 태스크 시작 시 주입됩니다.

environment에 넣으면 태스크 정의에 평문으로 남고 콘솔에서 그대로 보입니다.

이때 필요한 권한은 Task Execution Role에 있어야 합니다 — Task Role이 아닙니다. 이걸 헷갈려 태스크가 안 뜨는 경우가 흔합니다.

Fargate와 EC2 모드 중 무엇을 고르는가?200~300

Fargate: 서버 관리 없음, 태스크별 마이크로 VM 격리, 빠른 시작. 대신 단가가 높고 GPU·대용량 로컬 스토리지 같은 EC2 고유 기능을 못 씁니다.

EC2: 예약 인스턴스·Savings Plan으로 단가를 낮출 수 있고, 인스턴스 커스터마이징이 가능합니다. 대신 용량 공급자·패치·AMI를 직접 관리해야 합니다.

2025년 9월 ECS Managed Instances가 추가돼 중간 선택지가 생겼습니다 — EC2 기능을 쓰면서 인스턴스 운영은 AWS가 합니다.

비용 최적화는 Fargate Spot을 weight로 섞는 것이 실무 답입니다.

ECS와 EKS 중 무엇을 고르는가?300

ECS: AWS 전용, 러닝 커브가 낮고 클러스터 요금이 없습니다. IAM·ALB·CloudWatch와의 통합이 자연스럽습니다.

EKS: 표준 쿠버네티스라 이식성이 있고 생태계(Helm, Argo CD, Operator)가 압도적입니다. 대신 클러스터 시간당 요금이 있고 러닝 커브가 큽니다.

판단 기준: 팀이 쿠버네티스를 운영할 역량과 필요가 있는가. AWS만 쓰고 워크로드가 단순하면 ECS로 충분하고, 멀티 클라우드·복잡한 스케줄링·풍부한 생태계가 필요하면 EKS입니다.
