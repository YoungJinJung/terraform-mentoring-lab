EKS 이해하기

구조

Control Plane

AWS가 관리합니다. API Server, etcd, Scheduler, Controller Manager. 다중 AZ에 자동 배치되고 사용자는 접근할 수 없습니다.

여기에 시간당 요금이 붙습니다 — ECS와의 가장 큰 비용 차이입니다.

Data Plane

워커 노드. 세 가지 선택지 — Managed Node Group(AWS가 AMI·업그레이드 관리), Self-managed(직접), Fargate(서버리스 파드).

여기에 EC2 요금이 붙습니다.

버전 정책 — 비용이 걸린 이야기 LEVEL 300

확장 지원은 요금이 6배입니다

EKS는 표준 지원 14개월 + 확장 지원 12개월 = 총 26개월 수명주기입니다.

클러스터 요금이 표준 지원 시간당 $0.10, 확장 지원 시간당 $0.60입니다. 업그레이드를 미루면 요금이 6배가 됩니다.

더 중요한 것: upgradePolicy.supportType의 기본값이 EXTENDED입니다. 즉 방치하면 자동으로 확장 지원에 진입해 과금이 시작됩니다. STANDARD로 두면 표준 지원 종료 시 자동 업그레이드되고 추가 요금이 없습니다.

한 번 확장 지원에 들어가면 정책을 되돌릴 수 없고, 표준 지원 버전으로 올려야 합니다.

접근 제어 — aws-auth는 끝났습니다 LEVEL 300

중요aws-auth ConfigMap은 공식 deprecated

오래된 자료는 전부 aws-auth ConfigMap을 편집하라고 합니다. AWS 문서는 이제 이를 deprecated로 명시하고 Access Entry를 권장합니다.

ConfigMap 방식의 문제는 명확했습니다 — 잘못 편집하면 아무도 클러스터에 들어갈 수 없게 되고, Kubernetes API로만 고칠 수 있어 복구가 불가능했습니다. Access Entry는 EKS API라 클러스터가 잠겨도 AWS 콘솔·CLI로 복구됩니다.

인증 모드는 셋 — CONFIG_MAP, API_AND_CONFIG_MAP, API. API 계열로 바꾸면 되돌릴 수 없으니 전환 전에 확인하세요.

terraform-aws-modules/eks도 v21에서 aws-auth 서브모듈을 완전히 제거했습니다.

EKS Auto Mode LEVEL 300

2024.12 신규운영 부담을 크게 줄이는 선택지

Auto Mode를 켜면 다음이 애드온이 아니라 내장 기능으로 자동 관리됩니다 — Karpenter 기반 컴퓨트 오토스케일링, EBS CSI 드라이버, AWS Load Balancer Controller, VPC CNI, CoreDNS, kube-proxy, Pod Identity Agent, GPU 드라이버.

노드는 Bottlerocket 기반 이뮤터블 AMI이고 SSH·SSM 접근이 불가능합니다. 노드 최대 수명이 21일로 강제되어 자동 패치됩니다.

비용: EC2 요금 위에 관리 수수료가 얹힙니다(인스턴스 타입별). 구매 옵션(On-Demand·RI·SP·Spot)과 무관하게 부과됩니다.

판단: 플랫폼 팀이 작고 클러스터 운영에 시간을 쓰기 어렵다면 강력한 선택지입니다. 반대로 노드에 직접 접근하거나 세밀하게 튜닝해야 하면 맞지 않습니다.

Terraform에서는 compute_config, storage_config, kubernetes_network_config.elastic_load_balancing 세 블록이 Auto Mode 활성화 세트입니다.

파드에 권한 주기

25분LEVEL 300

모듈 3에서 표로만 봤던 IRSA와 Pod Identity를 실제로 구성합니다.

IRSA의 동작

  1. OIDC Provider 등록 클러스터의 OIDC 발급자 URL을 IAM에 등록합니다.
  2. ServiceAccount 어노테이션 eks.amazonaws.com/role-arn에 Role ARN을 답니다.
  3. 토큰 주입 웹훅이 파드에 projected service account 토큰(JWT)을 마운트합니다.
  4. AssumeRoleWithWebIdentity AWS SDK가 그 JWT로 STS를 호출해 임시 자격 증명을 받습니다.

Pod Identity의 동작

  1. 애드온 설치 Pod Identity Agent를 클러스터에 설치합니다(Auto Mode면 자동).
  2. Association 생성 (클러스터, 네임스페이스, ServiceAccount) → IAM Role 매핑을 EKS API로 등록합니다.
  3. 환경변수 주입 웹훅이 파드에 AWS_CONTAINER_CREDENTIALS_FULL_URI를 넣습니다.
  4. Agent가 발급 SDK가 그 URI로 Agent에 요청하면 임시 자격 증명을 받습니다.

OIDC Provider가 없다는 것이 결정적 차이입니다.

권장세션 태그로 ABAC까지 300

Pod Identity는 발급되는 세션에 클러스터명·네임스페이스·ServiceAccount를 태그로 붙입니다. 그래서 IAM 정책에서 이렇게 쓸 수 있습니다.

"Condition": {"StringEquals": {"aws:PrincipalTag/kubernetes-namespace": "${s3:prefix}"}}

Role 하나로 여러 네임스페이스의 권한을 분리할 수 있어 Role 수가 폭발하지 않습니다. IRSA로는 어려운 일입니다.

IRSA가 여전히 필요한 경우: EKS가 아닌 쿠버네티스(EKS Anywhere, EC2 위 셀프 매니지드, OpenShift on AWS). Pod Identity는 EKS 전용입니다.

  • 리소스: Provisioner → NodePool, AWSNodeTemplate → EC2NodeClass, Machine → NodeClaim

consolidation이 하는 일 300

Karpenter는 주기적으로 "지금 이 파드들을 더 적은/저렴한 노드로 옮길 수 있나"를 계산해 노드를 통합합니다. Cluster Autoscaler에는 없는 기능이고, 비용 절감 효과가 큽니다.

대신 파드가 계속 옮겨 다니므로 PodDisruptionBudget을 반드시 설정해야 합니다. budgets로 시간대별 중단 예산도 걸 수 있습니다.

1.35 GAIn-place Pod Resize

Kubernetes 1.35에서 파드를 재생성하지 않고 CPU·메모리 requests/limits를 변경하는 기능이 GA됐습니다(alpha 1.27 → beta 1.33 → GA 1.35).

VPA도 updateMode: InPlaceOrRecreate로 이를 활용합니다 — 인플레이스를 시도하고 실패하면 재생성으로 폴백합니다.

세부 제약(메모리 축소, QoS 클래스 불변 등)은 실제 클러스터 버전의 문서를 확인하세요.

helm provider v3의 문법 변경 300

v2 → v3에서 블록이 속성으로 바뀌었습니다. 옛 코드가 그대로 안 돌아갑니다.

GitOps

모듈 4의 Atlantis가 인프라에 대한 GitOps였다면, 여기서는 애플리케이션에 대한 GitOps입니다. 원칙은 같습니다.

  • 단일 소스(SSOT) — Git이 원하는 상태를 정의합니다
  • 선언형 — 명령이 아니라 상태를 씁니다
  • 자동 동기화 — 컨트롤러가 Git과 클러스터를 비교해 차이를 메웁니다
  • 관측 가능 — 실제 상태와 목표 상태의 차이(drift)가 보입니다

Push 기반

CI가 kubectl apply나 helm upgrade를 호출합니다. 단순하지만 CI가 클러스터 자격 증명을 가져야 하고, 클러스터의 실제 상태를 지속적으로 감시하지 않습니다.

Pull 기반

클러스터 안의 컨트롤러(Argo CD·Flux)가 Git을 주기적으로 당겨 적용합니다. 외부에 자격 증명을 주지 않고, drift를 자동으로 되돌립니다.

Argo CD 3.0의 breaking change 300

2.x에서 올릴 때 걸리는 것들입니다.

  • fine-grained RBAC이 하위 리소스에 전파되지 않습니다 — update/*, delete/* 정책을 별도로 줘야 합니다
  • logs RBAC이 기본 강제됩니다
  • 리소스 트래킹 기본값이 label → annotation
  • 고빈도 리소스(Endpoints, Lease 등)가 기본 제외
  • argocd-cm의 레거시 repository 설정 제거 → Secret 선언형 관리 필수

GitHub Actions 러너를 클러스터에서 — ARC

모듈 5에서 미뤄둔 이야기입니다. Actions Runner Controller가 잡이 큐에 들어오면 러너 파드를 띄우고 끝나면 정리합니다.

  • Helm 차트 두 개 — gha-runner-scale-set-controller(컨트롤러) + gha-runner-scale-set(러너 세트)
  • 인증은 GitHub App 또는 PAT
  • 컨테이너 모드는 kubernetes 또는 dind
  • GitHub이 공식 지원하는 것은 autoscaling runner scale sets 모드뿐입니다. 레거시 RunnerDeployment 방식은 커뮤니티 유지보수입니다

이걸 쓰면 러너가 VPC 안에 있으므로 프라이빗 리소스 접근 문제가 해결되고, Pod Identity로 AWS 권한도 자연스럽게 붙습니다.

클러스터 요금이 표준 시간당 $0.10, 확장 시간당 $0.60으로 6배 차이가 납니다.

가장 중요한 함정: upgradePolicy.supportType의 기본값이 EXTENDED라 방치하면 자동으로 과금이 시작됩니다. STANDARD로 두면 표준 지원 종료 시 자동 업그레이드되고 추가 요금이 없습니다. 한 번 확장 지원에 들어가면 되돌릴 수 없습니다.

EKS 접근 제어에서 aws-auth ConfigMap과 Access Entry의 차이는?300

aws-auth ConfigMap은 공식 deprecated입니다. Access Entry가 권장 방식입니다.

ConfigMap 방식의 결정적 문제: 잘못 편집하면 아무도 클러스터에 들어갈 수 없고, 고치려면 Kubernetes API가 필요한데 그게 막힌 상태라 복구 불가였습니다. Access Entry는 EKS API라 AWS 콘솔·CLI로 복구됩니다.

인증 모드는 CONFIG_MAP, API_AND_CONFIG_MAP, API 셋이고, API 계열로 바꾸면 되돌릴 수 없습니다.

terraform-aws-modules/eks도 v21에서 aws-auth 서브모듈을 완전히 제거했습니다.

IRSA와 Pod Identity를 비교하라300

IRSA는 클러스터마다 IAM OIDC Provider를 만들고 ServiceAccount 어노테이션 + AssumeRoleWithWebIdentity로 동작합니다. 클러스터가 늘 때마다 Role의 신뢰 정책을 갱신해야 하고, 계정당 OIDC Provider 100개 한도가 있습니다.

Pod Identity는 OIDC가 없습니다. Agent 애드온 + (클러스터·네임스페이스·SA) → Role 매핑으로 동작하고, 신뢰 주체는 pods.eks.amazonaws.com 하나입니다.

Pod Identity의 추가 이점: 세션 태그로 ABAC이 가능해 Role 하나로 네임스페이스별 권한을 나눌 수 있습니다. 2025년 6월부터 role chaining으로 크로스 계정도 됩니다.

IRSA가 필요한 경우: EKS가 아닌 쿠버네티스. Pod Identity는 EKS 전용입니다.

Cluster Autoscaler와 Karpenter의 차이는?300

Cluster Autoscaler는 미리 만들어둔 ASG의 desired를 조절합니다. 인스턴스 타입이 ASG에 고정돼 있고, ASG를 거치므로 프로비저닝이 느립니다.

Karpenter는 Groupless입니다. Pending 파드의 실제 요구(CPU·메모리·아키텍처·토폴로지)를 보고 인스턴스 타입을 직접 골라 EC2 API로 바로 띄웁니다. 훨씬 빠르고 낭비가 적습니다.

Karpenter의 킬러 기능은 consolidation — 파드를 더 적거나 저렴한 노드로 재배치해 노드를 통합합니다. Spot·On-Demand 비율도 조절합니다.

대가: 파드가 자주 옮겨 다니므로 PodDisruptionBudget이 필수입니다.

Karpenter v1에서 무엇이 바뀌었나?300

리소스 이름: Provisioner → NodePool, AWSNodeTemplate → EC2NodeClass, Machine → NodeClaim.

필드: WhenUnderutilized → WhenEmptyOrUnderutilized, consolidateAfter가 필수, ttlSecondsUntilExpired → expireAfter, kubelet 설정이 NodePool에서 EC2NodeClass로 이동, amiSelectorTerms 필수화.

추가: disruption budgets로 reason별·시간대별 중단 예산 지정.

v1.1.0부터 v1beta1 지원이 제거됐습니다. 옛 매니페스트는 동작하지 않습니다.

EKS Auto Mode는 무엇을 자동화하는가?300

Karpenter 기반 컴퓨트 오토스케일링, EBS CSI, AWS Load Balancer Controller, VPC CNI, CoreDNS, kube-proxy, Pod Identity Agent, GPU 드라이버를 애드온이 아니라 내장 기능으로 관리합니다.

노드는 Bottlerocket 기반 이뮤터블 AMI이고 SSH·SSM 접근 불가, 최대 수명 21일로 강제 교체됩니다.

비용은 EC2 요금 위에 관리 수수료가 얹힙니다.

판단: 플랫폼 팀이 작으면 강력한 선택지, 노드 접근이나 세밀한 튜닝이 필요하면 맞지 않습니다.

EKS에서 IP가 고갈되는 이유와 대응은?300

VPC CNI가 파드마다 VPC의 실제 IP를 할당하고, 노드는 ENI마다 보조 IP를 미리 확보(warm pool)하므로 실제 파드 수보다 더 많이 소모합니다.

대응 순서: ① 서브넷을 애초에 크게(/20 이상) ② Secondary CIDR(100.64.0.0/10 CGNAT 대역)을 추가해 파드 전용 서브넷 구성 ③ WARM_IP_TARGET·MINIMUM_IP_TARGET 조정 ④ 프리픽스 위임 모드로 /28 단위 할당.

①이 안 됐을 때 ②로 간다는 순서까지 말하면 좋습니다.

Push 기반과 Pull 기반 GitOps의 차이는?200~300

Push는 CI가 kubectl apply·helm upgrade를 호출합니다. 단순하지만 CI가 클러스터 자격 증명을 가져야 하고, 배포 이후의 drift를 감지하지 못합니다.

Pull은 클러스터 안 컨트롤러(Argo CD·Flux)가 Git을 당겨 적용합니다. 외부에 자격 증명을 주지 않고, drift를 자동으로 되돌립니다(self-heal).

멀티 클러스터에서 Pull이 특히 유리합니다 — CI가 모든 클러스터의 자격 증명을 갖지 않아도 됩니다.

Argo CD와 Flux 중 무엇을 고르는가?300

둘 다 CNCF Graduated이고 핵심 기능은 비슷합니다.

Argo CD: 단일 Application/ApplicationSet CRD, 내장 웹 UI와 자체 RBAC/SSO. 멀티 테넌시와 가시성이 강점입니다.

Flux: 컨트롤러 분리형(GitRepository·Kustomization·HelmRelease), 이미지 자동 업데이트가 본체에 포함. 쿠버네티스 네이티브한 조합이 강점입니다.

구체적 차이 하나: Argo CD의 이미지 자동 업데이트는 별도 프로젝트인데 스스로 프로덕션 비권장이라 명시하고 있습니다. 이미지 자동화가 중요하면 Flux가 유리합니다.

Helm의 Chart · Repository · Release를 구분하라200

Chart는 매니페스트 템플릿 + 기본값(values.yaml)의 패키지, Repository는 차트 저장소(요즘은 ECR 같은 OCI 레지스트리), Release는 차트를 특정 값으로 클러스터에 설치한 인스턴스입니다.

Release는 이름과 버전 이력이 있어 helm rollback이 가능합니다.

2025년 11월 Helm 4가 나왔고(server-side apply, Wasm 플러그인), Helm 3의 버그 수정은 2026년 7월에 종료됐습니다. 다만 Terraform helm provider는 아직 Helm 4 미지원입니다.

Terraform으로 쿠버네티스 리소스를 관리해도 되는가?300

경계를 나눠야 합니다. Terraform은 클러스터와 그 부속 인프라(VPC, 노드그룹, IAM, 애드온, Karpenter 같은 플랫폼 컴포넌트)까지, 애플리케이션은 GitOps 컨트롤러가 담당하는 것이 일반적입니다.

이유: 애플리케이션은 배포 주기가 훨씬 빠르고, Terraform state에 파드 수준 리소스를 넣으면 apply가 느려지고 충돌이 잦습니다. 또 클러스터가 아직 없는 상태에서 kubernetes provider를 구성하면 plan 단계에서 실패합니다(chicken-and-egg).

실무 패턴: Terraform이 클러스터 + Argo CD까지 설치하고, 그다음부터는 Argo CD가 자기 자신을 포함해 애플리케이션을 관리(app-of-apps).

Argo CD 3.0으로 올릴 때 주의할 점은?300

fine-grained RBAC이 하위 리소스에 전파되지 않습니다 — update/*, delete/* 정책을 별도로 줘야 기존과 같이 동작합니다.

그 외: logs RBAC 기본 강제, 리소스 트래킹 기본값이 label → annotation, 고빈도 리소스(Endpoints·Lease) 기본 제외, argocd-cm의 레거시 repository 설정 제거로 Secret 선언형 관리 필수.

GitHub Actions 러너를 EKS에서 운영하는 이유와 방법은?300

이유: 러너가 VPC 안에 있어 프라이빗 리소스에 접근할 수 있고, Pod Identity로 AWS 권한을 자연스럽게 부여할 수 있습니다. 잡마다 임시 파드라 격리도 좋습니다.

방법: ARC(Actions Runner Controller). Helm 차트 두 개 — gha-runner-scale-set-controller와 gha-runner-scale-set. 인증은 GitHub App 또는 PAT, 컨테이너 모드는 kubernetes 또는 dind.

주의: GitHub이 공식 지원하는 것은 autoscaling runner scale sets 모드뿐이고, 레거시 RunnerDeployment 방식은 커뮤니티 유지보수입니다.

PodDisruptionBudget은 왜 필요한가?300

자발적 중단(voluntary disruption) — 노드 드레인, Karpenter consolidation, 클러스터 업그레이드 — 시 동시에 내려갈 수 있는 파드 수의 하한/상한을 정합니다.

없으면 Karpenter가 노드를 통합하면서 같은 서비스의 파드를 한꺼번에 내려 서비스가 끊길 수 있습니다.

주의: PDB를 너무 빡빡하게(minAvailable을 replica 수와 같게) 걸면 노드 드레인이 영원히 끝나지 않아 업그레이드가 막힙니다. replica를 충분히 두고 여유를 남기세요.
