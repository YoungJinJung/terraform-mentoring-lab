02

DevOps와 IaC

25분

Terraform 문법으로 바로 들어가기 전에, 이 도구가 어떤 문제를 풀려고 나왔는지를 잡습니다.

DevOps를 지탱하는 다섯 가지

  • 문화(Culture) — 개발과 운영을 나누지 않고 하나의 팀으로
  • 자동화(Automation) — 사람이 반복하지 않게
  • 측정(Measurement) — 지표로 개선 여부를 확인
  • 공유(Share) — 알고 있는 것을 팀에 남김
  • 축적(Pile Up) — 기록을 쌓아 다음에 더 잘함

이 중 자동화·측정·공유가 인프라 영역으로 넘어온 결과물이 IaC입니다.

파이프라인에서 IaC의 자리

소스 → 빌드 → 테스트 → 배포 → 운영. 이 다섯 단계 전부가 어떤 인프라 위에서 돌아갑니다. IaC는 특정 단계가 아니라 파이프라인 전체를 떠받치는 바닥입니다.

단계인프라로 표현하면
SourceRepository, 라이브러리 저장소, 보안 검사
BuildCI 도구, 빌드 이미지 / Golden AMI
TestTesting as Code, 부하 테스트 자동화
DeployDeployment as Code, Immutable, GitOps
OperateMonitoring as Code, Alerting as Code, 로그 관리

선언형과 명령형

명령형 (Imperative)

"어떻게 만들지"를 순서대로 지시합니다. AWS CLI, 셸 스크립트.

aws ec2 create-vpc --cidr-block 10.0.0.0/16

같은 스크립트를 두 번 돌리면 VPC가 두 개 생깁니다.

선언형 (Declarative)

"무엇이 있어야 하는지"만 씁니다. Terraform, CloudFormation.

resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

두 번 돌려도 VPC는 하나입니다. 현재 상태와 비교해서 차이만 반영하기 때문입니다.

IaC 도구 지형

도구성격특징
Terraform선언형 · 멀티 클라우드HCL. 프로바이더 생태계가 가장 넓음. 사실상 표준
OpenTofu선언형 · 멀티 클라우드Terraform 포크. MPL 2.0 오픈소스. 상태 암호화 등 자체 기능 보유
CloudFormation선언형 · AWS 전용YAML/JSON. AWS 신규 서비스 대응이 빠름. 다른 클라우드 불가
AWS CDK명령형 코드 → 선언형TypeScript·Python으로 작성, CloudFormation으로 합성
Pulumi명령형 코드 → 선언형일반 프로그래밍 언어 사용. 개발자 친화적
Ansible절차형 · 구성 관리인프라 프로비저닝보다 서버 내부 설정에 강함. Terraform과 병행

Terraform과 Ansible은 경쟁 관계가 아닙니다. Terraform이 서버를 만들고, Ansible이 그 안을 채우는 조합이 흔합니다.

그래서 왜 IaC인가

  • 일관성 — dev·staging·prod가 같은 코드에서 나옵니다. "운영에서만 안 되는" 문제가 줄어듭니다.
  • 신속성 — 새 환경 하나를 몇 분 안에 복제합니다.
  • 확장성 — 서브넷 20개를 만들 때 콘솔에서 20번 클릭하지 않습니다.
  • 투명성 — 누가 언제 무엇을 왜 바꿨는지가 Git 히스토리에 남습니다. 이게 사실 가장 큽니다.
03

Terraform과 TACOS

30분

도구 자체의 현재 상황과, 팀 단위로 쓸 때 반드시 따라붙는 TACOS 레이어를 봅니다.

Terraform이 하는 일

HashiCorp가 만든 인프라 프로비저닝 도구입니다. HCL이라는 자체 문법으로 원하는 상태를 쓰면, Terraform이 프로바이더를 통해 실제 API를 호출해 그 상태를 만듭니다.

  1. Write HCL로 원하는 인프라를 선언합니다.
  2. Plan 현재 상태(state)와 실제 인프라, 그리고 코드를 비교해 차이를 계산합니다.
  3. Apply 계산된 차이만큼만 프로바이더 API를 호출합니다.

이 세 단계 중 Plan이 Terraform의 진짜 가치입니다. 바꾸기 전에 무엇이 바뀔지 볼 수 있다는 것.

2026.09 기준버전과 라이선스 현황

Terraform 1.16.1이 최신 안정 버전입니다(1.16.0은 2026년 8월 26일 릴리스). HashiCorp는 최근 2개 마이너 릴리스에 대해 버그 수정을 제공하므로, 실무에서는 1.15 이상을 쓰는 것이 안전합니다.

2023년 8월 Terraform은 MPL 2.0에서 BSL 1.1로 라이선스를 바꿨습니다. 경쟁 제품을 만드는 목적이 아니라면 사내 사용에는 제약이 없지만, 이 변경이 OpenTofu 포크를 낳았습니다. 2025년 IBM이 HashiCorp를 인수했고, 라이선스 자체는 그대로입니다.

이 멘토링은 Terraform 기준으로 진행합니다. 배운 내용은 OpenTofu에도 거의 그대로 적용됩니다.

TACOS — 혼자 쓸 때와 팀으로 쓸 때

로컬에서 terraform apply를 치는 순간 세 가지 문제가 생깁니다. 내 PC의 권한으로 운영 인프라를 바꾸고, 다른 사람은 내가 뭘 했는지 모르고, 동시에 두 명이 apply하면 상태가 깨집니다.

이걸 푸는 도구군을 TACOS(Terraform Automation and COllaboration Software)라고 부릅니다.

Collaboration

Git으로 코드를 관리하고, PR에서 plan 결과를 함께 봅니다. 리뷰 없이는 인프라가 안 바뀝니다.

Remote Operation

로컬이 아니라 원격에서 실행합니다. 실행 결과가 모두에게 같은 형태로 공유됩니다.

Security

RBAC과 감사 로그. 사람에게 AWS 콘솔 권한을 주지 않고도 인프라를 바꿀 수 있게 됩니다.

도구 지형

  • HCP Terraform — HashiCorp 관리형(구 Terraform Cloud)
  • Atlantis — 오픈소스, 직접 호스팅. 모듈 4에서 이걸 씁니다
  • Spacelift · env0 · Scalr — 상용 SaaS
  • Digger · Terrateam — GitHub Actions 기반 경량 대안

05

HCL 기초 문법

60분 · 실습

이 장의 문법만으로 실무 코드의 80%가 설명됩니다. 나머지는 7장에서 다룹니다.

블록 구조

HCL의 모든 것은 블록입니다. 형태는 항상 같습니다.

resource "aws_s3_bucket" "demo"에서 resource가 블록 타입, aws_s3_bucket이 리소스 타입, demo가 내가 붙이는 이름입니다. 이 이름으로 다른 곳에서 참조합니다.

terraform 블록 — 버전 고정

버전 제약 기호

~> 6.0은 6.x 안에서만 올라갑니다(6.9 OK, 7.0 차단). ~> 6.1.0은 6.1.x 안에서만. >= 1.15.0은 상한이 없으니 required_version에만 쓰고 프로바이더에는 쓰지 마세요.

terraform init이 만드는 .terraform.lock.hcl은 반드시 커밋합니다. 팀 전체가 같은 프로바이더 버전을 쓰게 하는 파일입니다.

provider — 누구에게 요청할 것인가

default_tags는 이 프로바이더로 만드는 모든 리소스에 태그를 자동으로 붙입니다. 비용 추적할 때 이게 없으면 나중에 고생합니다.

resource — 만들 것

의존성은 참조로 자동 결정됩니다. aws_s3_bucket.demo.id를 쓰는 순간 Terraform은 버킷을 먼저 만들어야 한다는 걸 압니다. depends_on은 참조로 표현할 수 없는 관계에만 씁니다.

lifecycle — 사고 방지 장치

1.16 신규destroy = false

1.16부터 lifecycle에 destroy = false를 쓰면 해당 리소스를 삭제 대상에서 제외할 수 있습니다. prevent_destroy가 "삭제하려 하면 에러"라면, 이쪽은 "삭제 계획에 아예 안 넣음"에 가깝습니다.

data source — 이미 있는 것을 읽기

data source는 읽기 전용입니다. Terraform이 관리하지 않는 리소스를 참조하거나, AMI ID처럼 계속 바뀌는 값을 하드코딩하지 않기 위해 씁니다.

variable — 밖에서 받는 값

sensitive는 화면만 가립니다

sensitive = true는 CLI 출력에서 값을 (sensitive value)로 표시할 뿐, state 파일에는 평문으로 저장됩니다. 진짜로 남기지 않으려면 ephemeral = true를 쓰거나, 모듈 3에서 다룰 SOPS·Secrets Manager 조합을 씁니다.

값 우선순위 — 뒤에 오는 것이 이깁니다

  1. variable 블록의 default (가장 약함)
  2. 환경 변수 TF_VAR_이름
  3. terraform.tfvars
  4. terraform.tfvars.json
  5. *.auto.tfvars / *.auto.tfvars.json (파일명 사전순)
  6. -var / -var-file CLI 플래그 (가장 강함)

terraform.tfvars에 비밀 값을 넣고 .gitignore하는 방식은 팀에서는 못 씁니다. 그래서 모듈 3에서 SOPS를 씁니다.

locals — 안에서 계산하는 값

variable은 밖에서 받는 값, local은 안에서 만드는 값. 같은 표현식이 세 번 이상 반복되면 local로 뽑으세요.

output — 밖으로 내보내는 값

output은 두 가지 용도입니다. 사람이 보려고(terraform output), 그리고 다른 구성이 참조하려고(6장의 terraform_remote_state).

상태 관리

state가 뭔가

Terraform은 코드 · 상태 · 실제 인프라 세 가지를 비교합니다. state 파일은 "내가 마지막으로 만든 게 무엇이었는지"에 대한 Terraform의 기억입니다.

이 구조 때문에 drift가 생깁니다. 누군가 콘솔에서 손으로 보안 그룹을 고치면 실제와 state가 어긋나고, 다음 plan에서 Terraform이 되돌리려 합니다.

state 파일은 비밀 문서입니다

RDS 비밀번호, 인증서 키 같은 값이 평문으로 들어갑니다. Git에 절대 올리지 말고(.gitignore에 *.tfstate*), S3 버킷에는 암호화와 퍼블릭 차단을 반드시 겁니다.

원격 상태 — S3 backend

로컬 state는 혼자 쓸 때만 가능합니다. 팀으로 가는 순간 공유 저장소와 동시 실행 잠금이 필요합니다.

중요 · 최신DynamoDB는 이제 필요 없습니다

오래된 블로그와 강의는 전부 dynamodb_table로 잠금을 겁니다. Terraform 1.11부터 S3 자체 잠금(use_lockfile = true)이 정식 지원되고, dynamodb_table 인자는 deprecated 상태로 향후 마이너 버전에서 제거될 예정입니다.

새로 만드는 프로젝트라면 DynamoDB 테이블을 만들지 마세요. 잠금은 S3에 <key>.tflock 파일로 잡힙니다.

TERRAFORM

클릭하면 답이 열립니다. 먼저 스스로 답해 보고 여세요. 답을 외우는 것보다 왜 그런지 한 문장으로 말할 수 있는지가 중요합니다.

terraform plan은 정확히 무엇과 무엇을 비교하는가?기초

세 가지를 봅니다. 코드(.tf) = 원하는 상태, state = 마지막으로 만든 것의 기록, 실제 인프라 = 지금 존재하는 것.

plan은 먼저 state와 실제를 대조(refresh)해 최신화한 뒤, 그 결과를 코드와 비교해 차이를 계산합니다. "코드와 state를 비교한다"고만 답하면 refresh 단계를 빠뜨린 겁니다.

state 파일이 왜 필요한가? 없으면 안 되나?기초

Terraform이 만든 리소스와 코드 상의 주소를 매핑하기 위해서입니다. state가 없으면 aws_s3_bucket.demo가 어느 실제 버킷인지 알 수 없습니다.

또 매번 모든 리소스를 API로 조회하는 대신 state를 캐시로 써서 성능을 확보하고, 의존성 그래프와 메타데이터를 보관합니다.

이론적으로 매번 import할 수는 있지만 현실적이지 않습니다.

state를 원격에 두는 이유와, 잠금이 필요한 이유는?기초~중급

원격 저장의 이유는 공유입니다. 로컬 state는 나만 가지고 있어서 팀이 같은 인프라를 다룰 수 없습니다.

잠금은 동시 apply로 state가 깨지는 것을 막습니다. 두 명이 동시에 apply하면 나중 사람이 앞사람의 변경을 덮어써 리소스가 고아가 됩니다.

최신 정보: 예전에는 S3 + DynamoDB 조합이 정석이었지만, Terraform 1.11부터 S3 네이티브 잠금(use_lockfile = true)이 지원되고 dynamodb_table은 deprecated입니다. 이 답을 하면 최신 버전을 따라가고 있다는 신호가 됩니다.

count와 for_each 중 무엇을 언제 쓰는가?중급

기본은 for_each입니다. 주소가 인덱스가 아니라 키(aws_subnet.this["public-a"])이기 때문에, 목록 가운데를 지워도 나머지가 영향을 받지 않습니다.

count는 인덱스 기반이라 가운데 항목을 지우면 뒤의 것들이 밀리면서 전부 재생성됩니다.

count가 적절한 경우는 사실상 하나 — 0 또는 1로 리소스를 만들지 말지 결정하는 스위치입니다.

Terraform은 리소스 생성 순서를 어떻게 정하는가?기초~중급

코드에 쓴 순서와 무관합니다. 참조 관계로 의존성 그래프를 만들어 위상 정렬합니다. aws_subnet.a.vpc_id = aws_vpc.main.id라고 쓰는 순간 VPC가 먼저 만들어져야 한다는 걸 압니다.

참조로 표현되지 않는 숨은 의존성(예: IAM 정책 전파, IGW 연결)만 depends_on으로 명시합니다. depends_on을 남발하면 병렬성이 떨어집니다.

sensitive = true를 쓰면 값이 안전해지는가?중급

아닙니다. CLI 출력과 로그에서 (sensitive value)로 가려질 뿐, state 파일에는 평문으로 저장됩니다.

그래서 state 버킷에 암호화·접근 제어가 반드시 필요하고, 진짜로 남기지 않으려면 Terraform 1.10+의 ephemeral 값이나 write-only 속성을 쓰거나, 값 자체를 Secrets Manager에 두고 참조만 합니다.

이 질문은 "state가 비밀 문서라는 걸 아는지" 확인하는 질문입니다.

drift가 무엇이고 어떻게 대응하는가?중급

코드·state와 실제 인프라가 어긋난 상태입니다. 누군가 콘솔에서 손으로 보안 그룹을 고치면 발생합니다.

대응은 세 가지 중 하나입니다. ① 코드에 반영해 정상화 ② 그대로 apply해서 되돌리기 ③ 외부에서 계속 바뀌는 값이면 lifecycle { ignore_changes = [...] }로 무시.

근본 해결은 사람에게서 콘솔 쓰기 권한을 회수하는 것입니다. 모듈 4의 Atlantis가 그 답입니다.

이미 콘솔로 만든 인프라를 Terraform으로 가져오려면?중급~고급

예전에는 terraform import 명령으로 하나씩 가져오고 HCL을 손으로 썼습니다.

지금은 import 블록을 코드에 쓰고 plan으로 확인한 뒤 apply합니다. 코드에 흔적이 남고 리뷰가 가능하다는 게 장점입니다.

terraform plan -generate-config-out=generated.tf로 HCL 초안을 자동 생성할 수 있습니다. Terraform 1.16부터는 모듈 내부에서도 import 블록을 쓸 수 있습니다.

반대로 관리에서 빼고 실제 리소스는 남기려면 removed 블록을 씁니다.

.terraform.lock.hcl은 무엇이고 왜 커밋하는가?중급

프로바이더의 정확한 버전과 체크섬을 고정하는 파일입니다. terraform init이 만듭니다.

커밋하지 않으면 팀원마다, CI 실행마다 다른 프로바이더 버전이 설치되어 동일한 코드가 다른 결과를 낼 수 있습니다. 애플리케이션의 package-lock.json과 같은 역할입니다.

여러 플랫폼에서 쓴다면 terraform providers lock -platform=...으로 해시를 함께 넣어둡니다.

Terraform과 Ansible의 차이는? 경쟁 관계인가?기초

경쟁 관계가 아닙니다. Terraform은 선언형 프로비저닝 — 서버·네트워크·DB 같은 리소스를 만들고 없앱니다. Ansible은 절차형 구성 관리 — 이미 있는 서버 안에 패키지를 깔고 설정을 바꿉니다.

전형적인 조합은 Terraform이 인프라를 만들고 Ansible이 그 안을 채우는 것입니다.

다만 요즘은 불변 인프라(immutable) 흐름이라, 서버에 들어가 설정하기보다 이미지를 미리 굽고(Packer) 교체하는 방식을 더 많이 씁니다.

모듈은 언제 만드는가? 좋은 모듈의 조건은?중급

같은 구성이 두 번 이상 반복될 때 만듭니다. 한 번만 쓰는 것을 모듈로 감싸면 추상화 비용만 늘어납니다.

좋은 모듈의 조건: provider 블록을 넣지 않고(호출자의 provider를 물려받음), 모든 입력에 description과 타입을 달고, output을 넉넉히 내보내고, 중첩을 두 겹 이상 하지 않습니다.

외부 모듈은 반드시 버전을 고정합니다 — Registry는 version, Git은 ?ref=.

환경(dev/staging/prod)을 어떻게 분리하는가? workspace를 쓰나?중급~고급

실무에서는 대부분 디렉터리로 분리합니다(envs/dev, envs/prod). 환경마다 backend key와 tfvars가 다르고, prod에만 있는 리소스도 있기 때문입니다.

workspace는 같은 코드·같은 backend에서 state만 나누는 기능이라, 구성이 완전히 동일한 경우에만 적합합니다. 환경별로 크기나 구성이 다르면 코드가 조건문으로 뒤덮입니다.

또 workspace는 같은 자격 증명·같은 계정을 전제하는 경우가 많아, 계정을 분리한 환경에는 잘 맞지 않습니다.

Terraform 라이선스 변경과 OpenTofu는 어떤 상황인가?상식

2023년 8월 HashiCorp가 Terraform을 MPL 2.0에서 BSL 1.1로 변경했습니다. 경쟁 제품을 만드는 목적이 아니면 사내 사용에는 제약이 없지만, 이 변경이 커뮤니티 포크인 OpenTofu(MPL 2.0, Linux Foundation)를 낳았습니다.

2025년 IBM이 HashiCorp를 인수했고 라이선스는 그대로입니다.

기능 차이: Terraform은 Stacks·HCP Terraform 연동·Sentinel, OpenTofu는 state 암호화·provider의 for_each·OCI 레지스트리. 문법은 대부분 호환됩니다.

plan에서 -/+ 가 뜨면 무엇을 확인하는가?기초~중급

-/+는 삭제 후 재생성입니다. 다운타임과 데이터 손실이 발생할 수 있는 가장 위험한 신호입니다.

plan 출력에서 # forces replacement 주석이 붙은 속성을 찾습니다. 그게 재생성의 원인입니다.

재생성을 피해야 한다면: 이름 변경이면 moved 블록으로 주소만 옮기고, 실수를 막아야 하면 lifecycle { prevent_destroy = true }, 무중단이 필요하면 create_before_destroy = true를 씁니다.

팀에서 로컬 apply를 막으려면 어떻게 하는가?고급

사람에게서 인프라 변경 권한을 회수하고 자동화 주체에게만 부여합니다. 개발자 IAM에는 읽기 권한만 주고, apply는 CI나 Atlantis 같은 도구가 맡은 Role로만 수행합니다.

도구 계층에서는 TACOS(Terraform Automation and Collaboration Software)를 씁니다 — Atlantis(오픈소스), HCP Terraform, Spacelift, env0, Scalr 등.

효과는 세 가지입니다. PR에서 plan을 함께 리뷰(협업), 원격 실행으로 결과 공유(일관성), 감사 로그와 권한 분리(보안). 모듈 4에서 Atlantis로 직접 구성합니다.
