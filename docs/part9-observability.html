Observability의 기본

20분LEVEL 200

모니터링과 Observability

모니터링은 "미리 정해둔 질문에 답하는 것"입니다 — CPU가 80%를 넘었는가. Observability는 "예상하지 못한 질문에 답할 수 있는 상태"입니다 — 왜 어제 오후 3시에 특정 고객만 느렸는가.

세 가지 신호

신호답하는 질문비용 특성
Metrics얼마나? 언제부터? — 집계된 수치, 시계열저렴. 카디널리티가 높아지면 급증
Logs정확히 무슨 일이? — 개별 이벤트가장 비쌉니다. 수집량에 비례
Traces어디서 느려졌나? — 요청의 전체 경로샘플링으로 조절

Observability 비용은 인프라 비용을 넘길 수 있습니다

실제로 흔한 일입니다. 특히 로그가 그렇습니다. 대응 전략을 처음부터 세우세요.

  • 로그 레벨 — DEBUG를 프로덕션에서 켜두지 않습니다
  • 티어링 — 실시간 분석이 필요한 로그와 보관만 하는 로그를 분리
  • 샘플링 — 트레이스는 전부 보내지 않습니다
  • 카디널리티 — 태그에 user_id 같은 고유값을 넣지 않습니다. 메트릭 비용이 폭발합니다

SLI · SLO · 알람

  • SLI(Service Level Indicator) — 측정하는 지표. 예: 성공한 요청의 비율, p99 응답 시간
  • SLO(Service Level Objective) — 목표치. 예: 30일간 가용성 99.9%
  • Error Budget — SLO가 허용하는 실패량. 99.9%면 30일에 약 43분. 이 예산이 남아 있으면 배포를 계속하고, 소진되면 안정화에 집중합니다

알람은 "사람이 지금 행동해야 하는 것"만

알람이 많으면 아무도 보지 않게 됩니다(alert fatigue). 기준은 하나 — 이 알람이 울렸을 때 사람이 새벽에 일어나 할 일이 있는가. 없으면 대시보드에 두세요.

증상 기반(symptom-based)으로 거는 것이 원칙입니다. "CPU 80%"가 아니라 "사용자 요청의 1%가 실패 중"이 알람입니다.

AWS 인테그레이션 관련 리소스 4개가 제거되고 하나로 통합됐습니다.

제거: datadog_integration_aws, datadog_integration_aws_tag_filter, datadog_integration_aws_log_collection, datadog_integration_aws_lambda_arn

대체: datadog_integration_aws_account 하나. 기존 계정은 새 리소스로 import한 뒤 구버전 리소스를 state에서 제거해야 합니다.

그 외: datadog_monitor의 locked 속성 제거(권한은 datadog_restriction_policy로), datadog_application_key 데이터 소스 제거, Plugin Framework 전환으로 Terraform CLI 1.1.5 이상 필요.

인터넷의 대부분의 예제가 아직 v3 기준입니다. 이걸 알고 있으면 시간을 크게 아낍니다.

액세스 키를 주지 않습니다. Datadog의 AWS 계정이 우리 Role을 AssumeRole하는 구조이고, ExternalId로 confused deputy를 막습니다. 모듈 3에서 배운 패턴 그대로입니다.

알람 메시지에 런북 링크를 넣으세요

새벽 3시에 알람을 받은 사람이 무엇을 확인하고 무엇을 해야 하는지가 메시지 안에 있어야 합니다. 링크 하나가 대응 시간을 절반으로 줄입니다.

notify_no_data도 중요합니다 — 데이터가 안 오는 것 자체가 장애 신호인데, 기본값은 알리지 않습니다.

  10. 확인 질문 — 누군가 Datadog 콘솔에서 알람을 직접 수정하면 어떻게 되나요?

마지막 질문의 답

다음 terraform plan이 그것을 drift로 감지하고 코드 상태로 되돌립니다. 이것이 모니터링을 코드로 관리하는 이유입니다 — 콘솔에서 조용히 알람을 끄는 일이 불가능해집니다.

반대로 긴급 상황에서 콘솔로 빠르게 고쳐야 할 때도 있습니다. 그럴 때는 고친 뒤 반드시 코드에 반영하는 규칙을 세우세요.

04

Sumo Logic

35분LEVEL 200~300

로그 중심 플랫폼입니다. Datadog과 겹치는 부분이 있지만 로그 티어링과 SIEM에서 성격이 다릅니다.

Collector 두 종류

Hosted Collector

에이전트 설치가 필요 없습니다. API 키·IAM Role 같은 인증 정보만 설정하면 Sumo Logic이 직접 수집합니다.

AWS(CloudTrail, S3, CloudWatch)뿐 아니라 Slack·Atlassian·CrowdStrike 같은 SaaS 로그도 가져옵니다.

Installed Collector

호스트나 DaemonSet으로 에이전트를 설치합니다. 지정한 경로의 파일 로그나 컨테이너 로그를 수집합니다.

애플리케이션 로그처럼 외부에서 접근할 수 없는 것에 씁니다.

Data Tier — 로그 비용의 핵심 LEVEL 300

티어대상기능
Continuous실시간 모니터링이 필요한 로그 — 애플리케이션·보안·액세스 로그대시보드 · 모니터(알람) 지원
Frequent비교적 자주 검색하는 로그 — 개발·테스트, 제품 분석대시보드·알람 미지원, 검색만
Infrequent거의 안 보는 로그 — 디버그, OS 로그, 스레드 덤프수집은 매우 저렴, 분석 시 과금

티어링이 곧 비용 전략입니다

단가가 티어별로 크게 다릅니다. 모든 로그를 Continuous에 넣으면 비용이 감당이 안 되고, 모두 Infrequent에 넣으면 장애 대응이 안 됩니다.

실무 접근: 알람을 걸어야 하는 것만 Continuous, 사후 조사용은 Infrequent. 이 분류를 코드로 관리하면 "왜 이 로그가 비싼 티어에 있지"를 PR에서 논의할 수 있습니다.

여기서도 인증은 IAM Role 기반입니다. 액세스 키를 SaaS에 주지 않는 원칙이 계속 이어집니다.

LAB 02

로그 파이프라인 구성

  1. Sumo Logic 트라이얼 계정을 만들고 액세스 ID·키를 SOPS로 관리합니다.
  2. Sumo Logic이 AssumeRole할 IAM Role을 만듭니다.
  3. Hosted Collector와 CloudWatch source를 만들어 모듈 8의 EKS 로그를 흘려보냅니다.
  4. Field Extraction Rule로 로그에서 level, trace_id를 뽑습니다.
  5. 에러 급증 모니터를 만들고, 애플리케이션에서 일부러 에러를 발생시켜 알람이 오는지 확인합니다.
  6. 티어 실험 — 디버그 로그를 Infrequent로 보내는 규칙을 추가하고, 검색 시 어떻게 다른지 확인하세요.
  7. 확인 질문 — Datadog과 Sumo Logic을 둘 다 쓰면 로그를 두 번 수집하게 됩니다. 어떻게 나눌 건가요?

마지막 질문에 대해

정답은 없지만 흔한 분리는 이렇습니다 — APM·메트릭·실시간 알람은 Datadog, 장기 보관과 보안 로그 분석(SIEM)은 Sumo Logic.

둘 다 쓰는 것 자체가 비용이므로, 하나로 통합하는 것이 대체로 낫다고 답해도 좋은 답입니다. 중요한 것은 중복 수집이 비용을 두 배로 만든다는 것을 인지하는가입니다.

OBSERVABILITY
모니터링과 Observability의 차이는?200

모니터링은 미리 정해둔 질문에 답합니다 — "CPU가 80%를 넘었나". Observability는 예상하지 못한 질문에 답할 수 있는 상태입니다 — "왜 어제 오후 3시에 특정 고객만 느렸나".

실무적으로는 메트릭·로그·트레이스를 연결해 임의의 질문에 답할 수 있는가로 갈립니다. 트레이스에서 특정 요청을 찾고 그 시점의 로그로 바로 갈 수 있으면 Observability입니다.

메트릭·로그·트레이스를 언제 무엇으로 보는가?200~300

메트릭은 "얼마나·언제부터" — 집계된 시계열. 저렴하지만 개별 요청을 알 수 없습니다.

로그는 "정확히 무슨 일이" — 개별 이벤트. 가장 비쌉니다.

트레이스는 "어디서 느려졌나" — 마이크로서비스 간 요청 경로.

전형적 흐름: 메트릭 알람으로 인지 → 트레이스로 범위 좁히기 → 로그로 원인 확인.

Observability 비용을 어떻게 관리하는가?300

네 가지 축입니다. ① 로그 레벨 — 프로덕션에서 DEBUG를 켜두지 않습니다 ② 티어링 — 실시간 분석용과 보관용을 나눕니다(Sumo Logic의 Continuous/Frequent/Infrequent) ③ 샘플링 — 트레이스를 전부 보내지 않습니다 ④ 카디널리티 관리.

카디널리티를 강조하면 좋습니다 — 메트릭 태그에 user_id나 request_id 같은 고유값을 넣으면 시계열 개수가 폭발해 비용이 급증합니다. 그런 값은 로그나 트레이스에 넣습니다.

현실적인 이야기: Observability 비용이 인프라 비용을 넘는 경우가 실제로 흔합니다.

SLI·SLO·Error Budget을 설명하라300

SLI는 측정 지표(성공 요청 비율, p99 지연), SLO는 목표치(30일 가용성 99.9%), Error Budget은 SLO가 허용하는 실패량입니다.

99.9%면 30일에 약 43분의 예산이 있습니다.

운영에 쓰는 방식이 핵심입니다: 예산이 남아 있으면 배포 속도를 유지하고, 소진되면 기능 개발을 멈추고 안정화에 집중합니다. SLO가 개발과 운영의 갈등을 데이터로 조정하는 장치라고 답하면 좋습니다.

좋은 알람의 기준은?200~300

기준은 하나 — 이 알람이 울렸을 때 사람이 지금 할 일이 있는가. 없으면 대시보드에 두어야 합니다.

증상 기반(symptom-based)으로 겁니다. "CPU 80%"가 아니라 "사용자 요청의 1%가 실패 중"입니다. 원인 기반 알람은 시스템이 바뀔 때마다 낡습니다.

실무 디테일: 알람 메시지에 런북 링크를 넣고, notify_no_data를 켭니다 — 데이터가 안 오는 것 자체가 장애 신호인데 기본값은 알리지 않습니다.

모니터링 설정을 왜 코드로 관리하는가?300

세 가지입니다. ① 리뷰 — 알람 임계값 변경이 PR diff로 보입니다 ② 재현 — 새 환경에 같은 대시보드·알람을 즉시 복제합니다 ③ drift 감지 — 누군가 콘솔에서 조용히 알람을 끄면 다음 plan에서 잡힙니다.

③이 실무에서 특히 큽니다. "알람이 시끄러워서 껐는데 아무도 몰랐다"가 장애로 이어지는 일이 자주 있습니다.

단서를 달면 좋습니다: 긴급 상황에서 콘솔로 빠르게 고칠 수는 있어야 하고, 그 뒤 코드에 반영하는 규칙이 필요합니다.

SaaS 모니터링 도구에 AWS 접근 권한을 어떻게 주는가?300

액세스 키를 주지 않습니다. 벤더의 AWS 계정이 우리 IAM Role을 AssumeRole하도록 신뢰 정책을 구성하고, ExternalId로 confused deputy를 막습니다.

ExternalId가 없으면, 그 벤더를 쓰는 다른 고객이 우리 Role ARN을 알아내 접근을 시도할 수 있습니다. 벤더가 발급한 고유 값을 조건으로 걸어야 합니다.

모듈 3에서 배운 크로스 계정 패턴과 정확히 같습니다.

Datadog Terraform provider v4에서 무엇이 바뀌었나?300 · 최신

AWS 인테그레이션 리소스 4개가 제거되고 datadog_integration_aws_account 하나로 통합됐습니다(2026년 3월).

제거: datadog_integration_aws, _tag_filter, _log_collection, _lambda_arn. 기존 계정은 새 리소스로 import한 뒤 구버전을 state에서 제거해야 합니다.

그 외: datadog_monitor의 locked 제거(권한은 datadog_restriction_policy로), datadog_application_key 데이터 소스 제거, Terraform CLI 1.1.5 이상 필요.

인터넷 예제 대부분이 아직 v3 기준이라는 점을 알고 있으면 실무에서 시간을 아낍니다.

Sumo Logic의 Data Tier를 설명하라300

세 티어입니다. Continuous(실시간 모니터링 대상 — 대시보드·알람 지원), Frequent(자주 검색하지만 알람은 불필요 — 대시보드·알람 미지원), Infrequent(거의 안 보는 로그 — 수집은 매우 저렴하고 분석 시 과금).

핵심은 이것이 곧 비용 전략이라는 점입니다. 전부 Continuous면 비용을 감당할 수 없고, 전부 Infrequent면 장애 대응이 안 됩니다.

실무: 알람을 걸 것만 Continuous, 사후 조사용은 Infrequent. 이 분류를 코드로 관리하면 PR에서 논의할 수 있습니다.

OpenTelemetry를 쓰는 이유는?300

벤더 종속을 계측 계층에서 끊기 위해서입니다. 애플리케이션을 벤더 SDK가 아니라 OTel 표준으로 계측하면, 나중에 백엔드를 Datadog에서 다른 것으로 바꿔도 애플리케이션 코드를 고치지 않습니다 — Collector 설정만 바꿉니다.

AWS 맥락에서는 ADOT(AWS Distro for OpenTelemetry)가 EKS 애드온으로 제공되고, Operator가 Collector를 CRD로 관리합니다. 메트릭은 AMP, 트레이스는 X-Ray로 보냅니다.

CloudWatch만으로 충분한 경우는?200~300

AWS만 쓰고 서비스 수가 많지 않다면 충분한 경우가 많습니다. Application Signals가 서비스 맵·SLO·APM 수준의 기능을 제공하고, 2026년 2월부터 CloudWatch Observability EKS 애드온에서 기본 활성화됩니다.

SaaS로 가는 이유는 대개 멀티 클라우드·온프레미스 통합, 더 나은 UI와 상관관계 분석, RUM·Synthetic 같은 프런트엔드 영역입니다.

비용 비교를 언급하면 좋습니다 — CloudWatch도 커스텀 메트릭과 로그 수집량이 늘면 결코 싸지 않습니다.

인프라를 코드로 관리한다고 할 때, 어디까지가 "전부"인가?300

판단 기준은 하나입니다 — 지금 이 환경을 전부 지우고 코드만으로 재현할 때, 사람이 콘솔에 들어가 손으로 해야 하는 일이 있는가.

흔히 빠지는 것들: 모니터링 알람·대시보드, GitHub 리포 설정과 브랜치 보호, SaaS 연동, DNS 레코드, 온콜 스케줄, 시크릿 값 자체.

현실적인 단서: 100%는 목표가 아니라 방향입니다. 남은 것을 명시적으로 문서화해 두는 것까지가 실무입니다.
