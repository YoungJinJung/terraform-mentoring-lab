CI · CD · CD

용어정의끝나는 지점
Continuous Integration변경을 자주 메인 브랜치에 통합하고, 매 커밋마다 자동 빌드·테스트빌드 산출물 생성
Continuous Delivery언제든 배포 가능한 상태로 유지. 배포 버튼은 사람이 누름스테이징까지 자동, 프로덕션은 수동 승인
Continuous Deployment테스트를 통과하면 사람 개입 없이 프로덕션까지프로덕션 자동 배포

둘 다 CD라서 헷갈립니다. 구분 기준은 하나 — 프로덕션 배포에 사람의 승인이 필요한가. 대부분의 조직은 Delivery까지 하고, Deployment는 신뢰할 만한 테스트 커버리지와 관측이 갖춰진 뒤에 갑니다.

CI의 원칙

  • 작고 잦은 커밋. 통합 주기가 길수록 충돌 해결 비용이 기하급수적으로 커집니다
  • 단일 메인 브랜치. 장수 브랜치(long-lived branch)를 만들지 않습니다
  • 모든 커밋을 테스트. 회귀를 즉시 잡습니다
  • 빌드는 빨라야 합니다. 10분을 넘으면 사람들이 기다리지 않고 다른 일을 하다가 컨텍스트를 잃습니다
  • 빌드 산출물은 한 번만 만듭니다. dev·staging·prod에 같은 아티팩트를 배포해야 "스테이징에선 됐는데"가 사라집니다

"한 번 빌드, 여러 번 배포"가 핵심입니다

환경마다 다시 빌드하면 그건 서로 다른 아티팩트입니다. 이미지 태그를 latest가 아니라 커밋 SHA로 붙이고, 환경 차이는 설정 주입으로만 처리하세요.

이 원칙이 모듈 6·7·8에서 계속 반복됩니다.

현실적인 조합

하나만 쓰는 조직은 드뭅니다. 흔한 형태는 GitHub Actions가 빌드·테스트를 하고, AWS 쪽 배포는 CodeBuild/CodeDeploy나 Jenkins가 담당하는 것입니다.

이유는 네트워크와 권한입니다. GitHub Actions의 호스티드 러너는 VPC 밖에 있어 프라이빗 서브넷의 RDS나 내부 엔드포인트에 닿지 못합니다. 그래서 VPC 안에서 도는 실행 주체가 하나 필요합니다.

이 멘토링에서는 GitHub Actions(빌드) + CodeBuild/Jenkins(배포) 조합을 만듭니다.

GitHub Actions 러너를 VPC 안에 두는 방법 LEVEL 300

  • CodeBuild가 호스팅하는 러너 — CodeBuild 프로젝트를 "runner project"로 만들고 웹훅을 연결하면, 잡 하나당 임시 빌드 하나가 self-hosted runner로 뜹니다. runs-on: codebuild-<project>-${{ github.run_id }}-${{ github.run_attempt }}
  • ARC(Actions Runner Controller) — EKS에서 러너를 오케스트레이션. 모듈 8에서 다룹니다
  • EC2 self-hosted runner — 가장 단순하지만 관리 부담이 큽니다
03

AWS Code Series

30분LEVEL 200~300

CodeBuild

완전 관리형 빌드 서비스입니다. buildspec.yml로 빌드 단계를 정의하고, 컨테이너 안에서 실행됩니다.

최신컴퓨트 옵션이 늘었습니다 300

Lambda compute — 콜드스타트가 거의 없고 자동 확장됩니다. 다만 Docker 빌드 불가, privileged 모드 불가, VPC 연결 불가, 캐시 불가, 최대 15분 고정입니다. 간단한 린트·테스트에 적합합니다.

Reserved capacity fleet — 전용 인스턴스를 상시 유지해 콜드스타트를 없앱니다. macOS 빌드는 이쪽에서만 가능합니다. 여러 프로젝트가 플릿을 공유하면 캐시도 공유되므로 보안상 주의하세요.

Docker Server — CodeBuild가 관리형 원격 Docker 서버를 붙여줍니다. 빌드 간 레이어 캐시가 유지되어 이미지 빌드가 크게 빨라집니다. 예전처럼 매 빌드마다 --cache-from을 수동으로 엮지 않아도 됩니다.

CodeDeploy

배포 오케스트레이터입니다. 네 가지 플랫폼을 지원합니다 — EC2/온프레미스, Lambda, ECS, CloudFormation.

플랫폼훅비고
EC2 in-placeApplicationStop → BeforeInstall → AfterInstall → ApplicationStart → ValidateService훅은 셸 스크립트. 타임아웃 최대 3600초
ECSBeforeInstall → AfterInstall → AfterAllowTestTraffic → BeforeAllowTraffic → AfterAllowTraffic훅은 Lambda 함수. 키가 대문자 Hooks:
LambdaBeforeAllowTraffic → AfterAllowTraffic훅은 Lambda 함수

자동 롤백은 "복원"이 아닙니다

CodeDeploy의 자동 롤백은 이전 상태로 되돌리는 게 아니라 마지막 정상 리비전을 새 배포로 다시 내보내는 것입니다.

그래서 이전 배포 스크립트가 만든 파일이나 DB 마이그레이션은 되돌아가지 않습니다. 롤백만 믿고 파괴적 마이그레이션을 하면 안 됩니다.

트리거는 두 가지 — 배포 실패, 또는 지정한 CloudWatch 알람 발동.

CodePipeline LEVEL 300

중요V1과 V2는 요금 모델이 다릅니다

V1은 활성 파이프라인당 월 단위 정액. V2는 액션 실행 분(minute)당 과금입니다. 파이프라인을 많이 만들지만 자주 안 돌린다면 V2가 저렴하고, 소수 파이프라인을 계속 돌린다면 V1이 유리할 수 있습니다.

V2에만 있는 기능: 파이프라인 변수, Git 트리거 필터(브랜치·태그·파일 경로), PARALLEL/QUEUED 실행 모드, 스테이지 조건(게이트), 스테이지 롤백, Commands 액션. 새로 만든다면 대체로 V2입니다.

스테이지 조건은 파이프라인 게이트입니다. 스테이지 진입 전 CloudWatch 알람 상태를 확인하거나, 배포 윈도우(예: 금요일 오후 배포 금지)를 강제하거나, Lambda로 커스텀 검사를 돌릴 수 있습니다.

CodeCommit에 대한 오해 정정

2024년 7월 신규 고객 대상 리포지토리 생성이 막혀 "종료됐다"고 알려졌지만, 2025년 11월 AWS가 전면 GA로 복귀시켰습니다. 신규 가입이 다시 열렸고 가격·SLA도 유지됩니다.

다만 실무에서 새로 시작한다면 여전히 GitHub/GitLab을 쓰는 경우가 압도적입니다. 면접에서 이 타임라인을 정확히 말하면 최신 정보를 따라간다는 신호가 됩니다.

04

Jenkins

30분LEVEL 200~300

아직도 가장 많이 쓰이는 CI 서버입니다. 왜 여전히 쓰는지와 무엇이 부담인지를 함께 봅니다.

구조

  • Controller(구 Master) — 웹 UI, 잡 정의, 스케줄링. 여기서 빌드를 돌리면 안 됩니다
  • Agent(구 Slave) — 실제 빌드 실행. Static(상시 서버)과 Dynamic(EC2·쿠버네티스에서 필요할 때 생성)
  • Plugin — 수천 개. 강점이자 약점입니다

코드로 관리하기

JCasC (Configuration as Code)

Jenkins 설정 자체를 YAML로 선언합니다. 보안 설정, 자격 증명, 도구 위치, 클라우드 에이전트 설정.

CASC_JENKINS_CONFIG 환경변수로 파일·디렉터리·HTTP URL을 지정합니다. 재시작 없이 reload됩니다.

Job DSL

잡 정의를 Groovy로 생성합니다. seed job 하나가 수십 개 잡을 만들어냅니다.

스크립트 보안 샌드박스와 함께 동작하므로 승인 흐름이 필요할 수 있습니다.

이 둘을 쓰지 않으면 Jenkins는 "설정이 UI에만 있는 블랙박스"가 됩니다. 서버가 죽으면 복구할 수 없습니다. IaC를 배우는 이 멘토링에서 Jenkins를 다루는 이유가 여기 있습니다.

2026 기준Jenkins 운영의 실제 부담

Java 요구 버전이 올라갔습니다. 2026년 4월 LTS(2.555.1)부터 Java 21 또는 25가 필요하고 Java 17은 지원되지 않습니다. 오래된 Jenkins를 올리려면 JVM부터 손봐야 합니다.

보안 권고가 거의 매월 나옵니다. 코어와 플러그인을 합쳐 한 번에 수십 건씩 공개되고, 역직렬화 RCE 같은 심각한 것도 포함됩니다. 미패치 상태로 인터넷에 노출된 Jenkins는 사실상 시한폭탄입니다.

그래서 실무 판단은 이렇게 갈립니다 — 새로 시작하면 GitHub Actions/CodeBuild, 이미 Jenkins가 깊이 박혀 있으면 유지하되 JCasC로 재현 가능하게 만들고 패치 주기를 세운다.

05

파이프라인 만들기

60분 · 실습

VPC에 넣으면 인터넷이 끊깁니다

CodeBuild를 vpc_config로 프라이빗 서브넷에 넣으면 NAT Gateway가 없으면 외부 패키지 저장소에 접근하지 못합니다. 모듈 2의 nat_strategy가 여기서 필요해집니다.

ECR·S3·Secrets Manager는 VPC Endpoint로 붙이면 NAT를 거치지 않아 비용이 줄어듭니다.

Role ARN은 비밀이 아니므로 vars에 둡니다. 액세스 키가 어디에도 없다는 것을 확인하세요 — 모듈 3에서 만든 OIDC의 결과입니다.

LAB 01

빌드·배포 파이프라인 구성

  1. ECR 리포지토리를 만들고, 이미지 스캔과 lifecycle policy(오래된 태그 정리)를 설정합니다.
  2. 간단한 애플리케이션(Spring Boot든 Node든)과 Dockerfile을 준비합니다. 모듈 6·7·8에서 계속 씁니다.
  3. GitHub Actions로 빌드해 ECR에 푸시합니다. 태그는 커밋 SHA로.
  4. Terraform으로 CodeBuild 프로젝트를 만듭니다. buildspec.yml에 캐시를 설정해 두 번째 빌드가 빨라지는지 확인하세요.
  5. Jenkins를 ECS Fargate에 띄웁니다. JCasC 설정 파일을 EFS나 S3에서 읽도록 구성합니다.
  6. Jenkins 파이프라인에서 CodeBuild를 호출하도록 연결합니다. Jenkins에는 AWS 액세스 키를 넣지 않습니다 — Task Role을 씁니다.
  7. 확인 — Jenkins 컨테이너를 지우고 다시 띄웠을 때 설정이 그대로 복원되나요? JCasC의 목적이 이것입니다.
  8. 확인 질문 — 왜 GitHub Actions만으로 끝내지 않고 CodeBuild를 두었나요?

마지막 질문의 답

네트워크와 권한입니다. GitHub 호스티드 러너는 VPC 밖이라 프라이빗 리소스에 닿지 못하고, IAM 권한도 OIDC로 열어줘야 합니다. VPC 안에서 도는 실행 주체가 하나 있으면 DB 마이그레이션, 내부 API 호출, 프라이빗 엔드포인트 접근이 자연스러워집니다.

이걸 "GitHub Actions만으로도 된다"고 답해도 틀린 건 아닙니다 — CodeBuild가 호스팅하는 GitHub Actions 러너를 쓰면 됩니다. 어느 쪽이든 이유를 말할 수 있으면 좋은 답입니다.

면접 단골 질문

CI/CD

클릭하면 답이 열립니다.

Continuous Delivery와 Continuous Deployment의 차이는?200

기준은 하나 — 프로덕션 배포에 사람의 승인이 필요한가.

Delivery는 언제든 배포 가능한 상태를 유지하되 배포 버튼은 사람이 누릅니다. Deployment는 테스트를 통과하면 사람 개입 없이 프로덕션까지 나갑니다.

Deployment로 가려면 신뢰할 수 있는 테스트 커버리지, 관측, 자동 롤백이 먼저 갖춰져야 합니다.

"한 번 빌드, 여러 번 배포"가 왜 중요한가?200~300

환경마다 다시 빌드하면 서로 다른 아티팩트가 됩니다. 의존성 버전이나 빌드 환경이 미세하게 달라져 "스테이징에선 됐는데 운영에선 안 되는" 상황이 생깁니다.

실무 구현: 이미지 태그를 latest가 아니라 커밋 SHA로 붙이고, 환경 차이는 설정 주입(환경변수, Parameter Store, ConfigMap)으로만 처리합니다.

덧붙이면 좋은 것: 이렇게 해야 롤백이 "이전 태그로 되돌리기"라는 단순한 작업이 됩니다.

Blue/Green 배포의 장단점은?200

장점: 롤백이 즉시입니다 — 트래픽만 되돌리면 됩니다. 전환 전에 새 환경을 실제로 테스트할 수 있습니다.

단점: 전환 기간 동안 리소스를 2배 씁니다. DB 스키마가 두 버전 모두와 호환되어야 합니다(하위 호환 마이그레이션 필요).

Rolling은 리소스가 덜 들지만 롤백이 느리고, 배포 중 두 버전이 섞여 돕니다.

CodeDeploy의 자동 롤백을 믿고 파괴적 마이그레이션을 해도 되는가?300

안 됩니다. CodeDeploy의 롤백은 이전 상태로 되돌리는 것이 아니라 마지막 정상 리비전을 새 배포로 다시 내보내는 것입니다.

그래서 배포 스크립트가 만든 파일이나 DB 스키마 변경은 되돌아가지 않습니다. 컬럼을 DROP하는 마이그레이션을 했다면 롤백해도 데이터는 사라진 채입니다.

원칙: 마이그레이션은 확장 후 축소(expand-contract)로 나눠 두 버전이 공존 가능하게 만듭니다.

CodePipeline V1과 V2의 차이는?300

요금 모델이 근본적으로 다릅니다. V1은 활성 파이프라인당 월 정액, V2는 액션 실행 분당 과금입니다.

V2 전용 기능: 파이프라인 변수, Git 트리거 필터(브랜치·태그·파일 경로), PARALLEL/QUEUED 실행 모드, 스테이지 조건(게이트), 스테이지 롤백, Commands 액션.

특히 스테이지 조건이 유용합니다 — CloudWatch 알람이 울리는 중이면 배포를 막거나, 배포 금지 시간대를 강제할 수 있습니다.

CodeBuild를 VPC에 넣으면 무엇이 달라지는가?300

프라이빗 서브넷의 RDS, 내부 엔드포인트에 접근할 수 있게 됩니다. DB 마이그레이션이나 내부 API 호출이 필요할 때 필수입니다.

대신 인터넷이 끊깁니다. NAT Gateway가 없으면 npm·Maven·PyPI 같은 외부 저장소에 접근하지 못합니다.

비용 최적화: ECR·S3·Secrets Manager·CloudWatch Logs는 VPC Endpoint로 붙이면 NAT 처리 요금을 아낍니다. 특히 컨테이너 이미지 풀이 큽니다.

CodeBuild의 Lambda compute는 언제 쓰는가?300

콜드스타트가 거의 없고 자동 확장되므로 짧고 잦은 작업에 좋습니다 — 린트, 단위 테스트, 간단한 스크립트.

못 쓰는 경우가 명확합니다: Docker 빌드 불가(privileged 모드 없음), VPC 연결 불가, 캐시 불가, /tmp만 쓰기 가능, 최대 15분 고정(타임아웃 조정 불가).

이미지 빌드는 일반 컴퓨트나 reserved capacity fleet을 씁니다.

Jenkins를 코드로 관리하려면?300

두 축입니다. JCasC로 Jenkins 설정(보안, 자격 증명, 클라우드 에이전트, 도구 경로)을 YAML로 선언하고, Job DSL로 잡 정의를 Groovy 코드로 생성합니다.

이유: 둘 다 없으면 Jenkins는 설정이 UI에만 있는 블랙박스가 되고, 서버가 죽으면 복구할 수 없습니다.

검증 방법도 말하면 좋습니다 — 컨테이너를 지우고 다시 띄웠을 때 설정이 그대로 복원되는지 확인합니다.

2026년에 Jenkins를 새로 도입할 이유가 있는가?200~300

새로 시작한다면 대개 없습니다. GitHub Actions나 CodeBuild가 관리 부담이 훨씬 적습니다.

Jenkins가 여전히 맞는 경우: 온프레미스 자원을 써야 하거나, 복잡한 승인·게이트 흐름이 있거나, 특정 레거시 도구 연동이 플러그인으로만 가능할 때.

도입 시 알아야 할 현실: 2026년 4월 LTS부터 Java 21 또는 25 필요(Java 17 미지원), 코어·플러그인 보안 권고가 거의 매월 나옵니다. 패치 주기를 세우지 않을 거면 도입하지 않는 편이 낫습니다.

GitHub Actions만으로 AWS 배포를 다 할 수 있나?300

대부분 됩니다. 다만 두 가지 제약이 있습니다.

네트워크 — 호스티드 러너는 VPC 밖이라 프라이빗 서브넷의 RDS나 내부 엔드포인트에 닿지 못합니다. 권한 — OIDC로 열어야 하고, 러너가 공용 인프라라는 점을 고려해야 합니다.

해결책: CodeBuild가 호스팅하는 GitHub Actions 러너(잡당 임시 빌드 하나), ARC로 EKS에서 러너 운영, 또는 배포 단계만 CodeBuild/Jenkins에 위임.

CI 빌드가 느릴 때 어디부터 보는가?200~300

순서대로: ① 캐시 — 의존성 캐시(Gradle·npm·pip)와 Docker 레이어 캐시가 실제로 히트하는지 ② 병렬화 — 독립적인 잡을 나눠 동시 실행 ③ 불필요한 단계 제거 — 변경 없는 경로는 건너뛰기(path filter) ④ 컴퓨트 크기.

AWS 맥락에서는 CodeBuild Docker Server가 빌드 간 레이어 캐시를 유지해 이미지 빌드를 크게 줄여주고, reserved capacity fleet이 콜드스타트를 없앱니다.

목표치를 말하면 좋습니다 — PR 피드백은 10분 이내가 실용적인 기준입니다.

CodeCommit은 지금 쓸 수 있는가?상식

쓸 수 있습니다. 2024년 7월 신규 고객 대상으로 리포지토리 생성이 막혀 "종료됐다"고 알려졌지만, 2025년 11월 AWS가 전면 GA로 복귀시켰습니다.

다만 실무에서 새로 시작할 때 GitHub/GitLab을 고르는 흐름은 그대로입니다 — 생태계와 협업 기능 차이가 큽니다.

파이프라인에 시크릿을 어떻게 주는가?300

원칙은 AWS 자격 증명은 시크릿으로 주지 않는 것입니다 — GitHub Actions는 OIDC, CodeBuild는 서비스 역할, Jenkins on ECS는 Task Role.

진짜 시크릿(외부 API 키 등)은 Secrets Manager나 Parameter Store에 두고 실행 시점에 주입합니다. CodeBuild는 buildspec의 env.secrets-manager·env.parameter-store로 직접 참조할 수 있습니다.

값 자체의 관리는 모듈 3의 SOPS로 — 암호화된 채 Git에 있고 Terraform이 복호화해 Secrets Manager에 넣습니다. 사람이 콘솔에서 입력하는 단계가 없습니다.

체크리스트 — 모듈 6으로 넘어가기 전에

  • Delivery와 Deployment를 구분해서 말할 수 있다
  • "한 번 빌드, 여러 번 배포"를 왜 지키는지 설명할 수 있다
  • Blue/Green의 대가(리소스 2배)를 안다
  • CodeDeploy 롤백이 "복원"이 아니라는 것을 안다
  • CodeBuild를 VPC에 넣을 때의 트레이드오프를 안다
  • ECR에 커밋 SHA 태그로 이미지를 푸시해 봤다
  • 액세스 키 없이 GitHub Actions에서 AWS에 인증해 봤다
  • Jenkins를 지웠다가 다시 띄워 설정이 복원되는 것을 확인했다
