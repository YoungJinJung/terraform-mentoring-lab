IMDSv2 LEVEL 300

인스턴스 메타데이터 서비스는 인스턴스 내부에서 169.254.169.254로 접근해 Instance Profile의 임시 자격 증명을 받아오는 통로입니다.

IMDSv1은 SSRF에 취약합니다

IMDSv1은 단순 GET 요청만으로 자격 증명을 반환합니다. 애플리케이션에 SSRF 취약점이 있으면 공격자가 그 경로로 인스턴스의 IAM 권한을 훔칠 수 있습니다. 실제 대형 유출 사고의 원인이었습니다.

IMDSv2는 PUT으로 토큰을 먼저 받고 그 토큰으로 조회하는 세션 방식이라 SSRF로는 뚫기 어렵습니다. 2024년 중반 이후 새로 출시되는 인스턴스 타입은 IMDSv2 전용이 기본이고, 계정 단위로 "새 인스턴스는 IMDSv2 기본" 설정도 가능합니다.

Terraform에서는 반드시 명시하세요:

hop_limit = 1이면 인스턴스 자신만 IMDS에 접근하고, 그 위에서 도는 컨테이너는 접근하지 못합니다. 컨테이너에 권한이 필요하면 Task Role을 쓰세요.

Launch Template — Launch Configuration은 끝났습니다

중요Launch Configuration은 만들 수 없습니다

2024년 10월 1일 이후 생성된 계정에서는 콘솔·API·CLI·CloudFormation 어떤 방법으로도 launch configuration을 만들 수 없습니다. 2023년 이후 나온 인스턴스 타입도 지원하지 않습니다.

옛날 블로그에 aws_launch_configuration이 나오면 그 자료는 낡은 것입니다. aws_launch_template을 쓰세요.

AMI 관리 — EC2 Image Builder LEVEL 300

"인스턴스를 띄우고 손으로 설정한 다음 AMI를 뜬다"는 방식은 재현이 안 됩니다. Golden AMI를 파이프라인으로 만드세요.

  • Component — 설치·설정·테스트를 YAML로 정의
  • Recipe — 베이스 이미지 + 컴포넌트 조합
  • Infrastructure Configuration — 빌드에 쓸 인스턴스 타입·서브넷
  • Distribution Settings — 리전 복제, KMS 암호화, 계정·조직 공유
  • Lifecycle Policy — 오래된 AMI 자동 정리

서비스 자체는 무료이고 EC2·S3·EBS 비용만 듭니다. 대안으로 HashiCorp Packer도 널리 쓰입니다.

  • 인스턴스에 SSH로 들어가 손으로 설정하기. 다음에 뜨는 인스턴스는 그 설정이 없습니다

  • Launch Template — 무엇을 띄울지(AMI, 타입, userdata, IAM, 메타데이터 옵션)

Health Check Grace Period

인스턴스가 뜨고 애플리케이션이 준비되기까지의 유예 시간입니다. 이게 짧으면 앱이 뜨기도 전에 unhealthy로 판정해 죽이고, 다시 띄우고를 반복합니다. Spring Boot처럼 기동이 느리면 넉넉히 주세요.

Instance Refresh — AMI 교체의 표준 방법 LEVEL 300

새 AMI로 인스턴스를 갈아끼울 때, ASG를 지웠다 만들지 않습니다. Instance Refresh가 순차 교체를 관리합니다.

auto_rollback의 기본값은 false입니다

새 AMI가 문제여서 인스턴스가 계속 unhealthy면, 기본 설정으로는 refresh가 실패한 채로 멈춥니다. 자동으로 이전 버전으로 돌아가지 않습니다. 반드시 켜세요.

또 max_instance_lifetime은 기본 동작이 "종료 후 신규 시작"이라 인스턴스가 하나뿐인 그룹에서는 다운타임이 생깁니다. instance maintenance policy로 "먼저 띄우고 나중에 종료"로 바꾸세요.

Blue/Green을 EC2에서 하는 두 가지 방법

CodeDeploy Blue/Green

CodeDeploy가 새 ASG를 통째로 만들고 ALB 타겟 그룹을 교체한 뒤 옛 ASG를 정리합니다.

훅으로 검증 단계를 넣을 수 있고, CloudWatch 알람 기반 자동 롤백이 됩니다.

ASG Instance Refresh

엄밀히는 Rolling입니다. 같은 ASG 안에서 인스턴스를 순차 교체합니다.

단순하고 추가 서비스가 필요 없지만, 롤백이 "다시 롤링"이라 즉시가 아닙니다.

이 실습에서는 CodeDeploy Blue/Green으로 갑니다. 모듈 7의 ECS Blue/Green과 비교하기 위해서입니다.

서비스 구성 흐름

20분LEVEL 200~300
  1. 빌드 모듈 5의 GitHub Actions가 애플리케이션을 빌드해 S3에 아티팩트로 올립니다. 컨테이너가 아니라 jar/zip입니다.
  2. 인프라 Instance Profile, ALB, 리스너, 타겟 그룹 두 개(blue/green), ASG를 Terraform으로 만듭니다.
  3. 배포 CodeDeploy가 새 ASG를 만들고 appspec.yml의 훅을 실행하며 아티팩트를 설치합니다.
  4. 전환 헬스체크를 통과하면 ALB 리스너가 green 타겟 그룹을 가리키고, 대기 시간 후 blue를 정리합니다.

ignore_changes를 빼면 Terraform과 CodeDeploy가 싸웁니다

CodeDeploy가 리스너의 타겟 그룹을 green으로 바꾸면, 다음 terraform plan이 그걸 drift로 보고 blue로 되돌리려 합니다. 배포한 버전이 apply 한 번에 원복되는 사고가 여기서 납니다.

이 문제는 "Terraform이 만드는 것"과 "배포 도구가 바꾸는 것"의 경계를 어디에 그을지의 일반적인 주제입니다. 모듈 7의 ECS에서도 desired_count·task_definition에 같은 고민이 반복됩니다.

면접 단골 질문

EC2 · 배포
IMDSv1과 IMDSv2의 차이, 그리고 왜 v2를 강제하는가?300

IMDSv1은 단순 GET으로 169.254.169.254에서 Instance Profile의 임시 자격 증명을 반환합니다. 애플리케이션에 SSRF 취약점이 있으면 공격자가 그 경로로 IAM 권한을 탈취할 수 있습니다.

IMDSv2는 PUT으로 토큰을 먼저 받고 그 토큰으로 조회하는 세션 방식이라 SSRF로 뚫기 어렵습니다.

Terraform에서는 http_tokens = "required". 추가로 http_put_response_hop_limit = 1을 주면 인스턴스 위의 컨테이너가 IMDS에 접근하지 못합니다.

2024년 중반 이후 새로 나오는 인스턴스 타입은 IMDSv2 전용이 기본입니다.

인스턴스를 Stop하면 요금이 안 나오는가?200

컴퓨팅 요금은 안 나오지만 EBS 볼륨 요금은 계속 나갑니다. Elastic IP도 보유하고 있으면 과금됩니다.

Terminate해도 볼륨의 delete_on_termination이 false면 볼륨이 남아 계속 과금됩니다.

Launch Configuration과 Launch Template 중 무엇을 쓰는가?200

Launch Template만 씁니다. Launch Configuration은 2023년 이후 출시된 인스턴스 타입을 지원하지 않고, 2024년 10월 1일 이후 생성된 계정에서는 아예 만들 수 없습니다.

Launch Template의 이점: 버전 관리, 여러 인스턴스 타입 혼합(mixed instances policy), Spot 통합, 메타데이터 옵션 지정.

ASG의 Health Check Type을 EC2와 ELB 중 무엇으로 하는가?200~300

웹 서비스라면 ELB입니다. EC2는 인스턴스가 살아있는지(하이퍼바이저 수준)만 보므로, 애플리케이션이 죽었는데 인스턴스는 healthy인 상태가 계속됩니다.

같이 언급하면 좋은 것: health_check_grace_period가 너무 짧으면 앱이 기동하기 전에 unhealthy 판정을 받아 죽이고 띄우기를 무한 반복합니다.

Instance Refresh로 AMI를 교체할 때 주의할 점은?300

auto_rollback의 기본값이 false입니다. 새 AMI가 문제여도 자동으로 되돌아가지 않고 refresh가 실패한 채 멈춥니다. 반드시 켜세요.

min_healthy_percentage(기본 90%)와 max_healthy_percentage를 조정해 "먼저 띄우고 나중에 종료"할지 "종료하고 띄울지"를 정합니다.

triggers = ["launch_template"]을 걸어두면 LT가 바뀔 때 자동으로 refresh가 시작됩니다.

EC2에서 Blue/Green 배포는 어떻게 하는가?300

CodeDeploy Blue/Green이 표준적인 방법입니다. CodeDeploy가 새 ASG를 통째로 만들고 아티팩트를 설치한 뒤, ALB 리스너의 타겟 그룹을 교체하고 대기 시간 후 옛 ASG를 종료합니다.

ASG Instance Refresh는 엄밀히는 Rolling입니다 — 같은 ASG 안에서 순차 교체하므로 롤백이 즉시가 아닙니다.

차이를 말하면 좋습니다: Blue/Green은 리소스 2배 + 즉시 롤백, Rolling은 리소스 절약 + 느린 롤백.

CodeDeploy가 리스너를 바꾸면 Terraform은 어떻게 되는가?300

Terraform이 그것을 drift로 보고 원래대로 되돌리려 합니다. 그러면 다음 apply에서 방금 배포한 버전이 원복되는 사고가 납니다.

해결: 리스너의 default_action에 lifecycle { ignore_changes = [...] }를 겁니다.

더 큰 주제로 확장하면 좋습니다 — "Terraform이 소유하는 것"과 "배포 도구가 바꾸는 것"의 경계를 명시적으로 정해야 합니다. ECS의 task_definition·desired_count에서도 같은 문제가 반복됩니다.

EC2에 접속할 때 SSH 대신 무엇을 쓰는가?200~300

SSM Session Manager입니다. 인바운드 포트를 열 필요가 없고, 키페어 관리도 필요 없으며, 세션 로그가 CloudTrail·CloudWatch에 남습니다.

필요 조건: 인스턴스에 SSM Agent(최신 AMI에는 기본 포함), Instance Profile에 AmazonSSMManagedInstanceCore, 그리고 인터넷이 없으면 SSM용 VPC Endpoint 3종(ssm, ssmmessages, ec2messages).

보안 그룹에 22번을 여는 것 자체가 안티패턴이라고 답하면 좋습니다.

AMI를 어떻게 관리하는가?300

손으로 인스턴스를 설정하고 이미지를 뜨는 방식은 재현이 안 됩니다. 파이프라인으로 굽습니다 — EC2 Image Builder나 Packer.

구성 요소: 컴포넌트(설치·설정·테스트를 YAML로), 레시피(베이스 + 컴포넌트), 배포 설정(리전 복제·KMS·계정 공유), 라이프사이클 정책(오래된 AMI 자동 정리).

덧붙이면 좋은 것: AMI에는 변하지 않는 것(런타임, 에이전트)만 넣고, 애플리케이션 아티팩트는 부팅 시 받아오거나 CodeDeploy로 설치합니다. 그래야 AMI를 자주 다시 굽지 않습니다.

Graviton으로 옮길 때 고려할 점은?300

ARM64 아키텍처이므로 바이너리와 컨테이너 이미지가 ARM용이어야 합니다. JVM·Go·Node·Python처럼 크로스 플랫폼인 스택은 대체로 문제없고, 네이티브 라이브러리를 쓰는 경우가 걸립니다.

실무 준비: docker buildx로 linux/amd64,linux/arm64 멀티 아키텍처 이미지를 함께 빌드해 두면 전환 비용이 크게 줄어듭니다.

2026년 기준 Graviton5 기반 M9g/M9gd가 GA입니다. 가격 대비 성능 이점이 있어 새로 만드는 워크로드는 ARM을 먼저 검토하는 것이 합리적입니다.

인스턴스에 상태를 두면 안 되는 이유는?200

ASG는 인스턴스를 언제든 종료하고 새로 띄웁니다 — 스케일 인, 헬스체크 실패, AMI 교체, 최대 수명 도달, Spot 회수.

그래서 로그는 CloudWatch/S3로, 세션은 ElastiCache나 DB로, 업로드 파일은 S3나 EFS로 빼야 합니다.

이게 불변 인프라(immutable infrastructure)의 전제이고, Blue/Green이 성립하는 이유이기도 합니다.
